Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

Late in August, deep into a long shaping session, the person running it told the agent that the conversation was about to be compacted: summarized, to free room for more work, with everything not in the summary gone from the agent's memory. The agent had been keeping a ledger all along — the running file where a session writes down what was decided, what it learned, and where the work stands, so it can find its way back after a compaction. To get ready, the agent rewrote that ledger into a short summary of the current state, and in doing so deleted the history it had built up over the session.

The person also named why this is the worst possible moment to rewrite anything. An agent whose memory is nearly full is at its least capable, so the rewrite is a summary made by the weakest version of the agent, under exactly the strain the ledger exists to protect against. Whatever it drops is gone for good once the compaction lands. Nothing in the file stopped the rewrite, and nothing afterwards would have shown that it had happened.

Today's way, and where it breaks

Today a ledger is a plain text file in the session's own folder. Agents add to it with ordinary shell commands, one line at a time, and read it the same way. In one session we followed from start to finish, the ledger was written 198 times and only ever read by its last few lines. It holds three kinds of things: what the person decided, what the session learned about the product while researching it, and where the work stands — what is running, on which branch, with which result.

It breaks in four places.

  • Anything can rewrite it. A file accepts any edit, so history gets replaced, as in the story above. When agents are told never to rewrite, the summary at the top goes stale instead: one ledger reached a size where its top section still described work from five days earlier.

  • Writing it can do damage. Because every entry goes in through the shell, the shell reads it first. One entry quoted four commands as a note for later: mark a pull request ready, merge it, tear down its workspace, remove a worktree.

  • Its times are made up. Agents type each entry's time from memory, and the times drift: minutes, hours, once a whole day. Writing the rule down did not help.

  • Finding anything gets more expensive every day. A finding from research sits somewhere in a long log, between launch notes and test results. Getting it back means searching a file that keeps growing, and reading the file costs more of the agent's memory the longer the session runs.

To cope, agents restate rules inside the ledger, read it by byte offsets once it outgrows a single read, and repair it by hand when a write goes wrong. None of it makes the record trustworthy again.

The outcome test

  1. Nothing written can be changed or removed by accident, and nothing can be changed quietly. An edit or a delete is refused by the database itself, not by a rule the agent is asked to follow. If someone goes around the database — removes its guards, rewrites or deletes the file — the next read says the record is no longer whole.

  2. What we learn about the product stays learned. A finding from research — how a piece of functionality behaves, why the code is the way it is, a premise that turned out false — is recorded the moment we have it, with where it came from. When the same question comes up later in the effort, the session finds the finding instead of researching it again.

  3. Whenever the session consults the record, it gets back exactly what was written. What the person decided, what the session learned, and where the work stands each come back in their original words, stamped with the real time they were written. What is still in force is shown apart from what was later superseded or corrected, and the superseded entries stay readable.

  4. Consulting the record costs the same on day one as on day ten. Finding an entry, or reading what is in force, takes the same small amount of reading however large the record grows.

Nobody forces the session to read the record at a fixed moment, such as right after a compaction. Agents already reach for the ledger when they need it; the record has to be there, whole and quick to search, when they do.

Why now

Two things changed this week. Ledgers moved out of a temporary folder the computer could wipe and into each project's own session folder, so the file now survives. Compaction now happens on its own, whenever the agent's memory fills, rather than when someone announces it — so there is no longer a moment to prepare, and what the session wrote down along the way is all it gets back. The ledger is now the one record every long session leans on, and the remaining question is whether it still says what was written. This pays in time: every lost or doubtful entry is research done twice, or a session spent rebuilding state.

The big hire and the little hires

The big hire is the person who upgrades the package in a project: from then on, every session there keeps its ledger in the database. To make that switch they must lose nothing they have today, and one thing they have today is a ledger anyone can open. People read ledgers directly, copy them, and have rebuilt a lost one by hand. So the whole record has to stay readable as plain text, by a person as easily as by an agent.

The little hires are the agents, every time they write an entry or look something up, and this is where the switch really gets decided. Adding a line to a file costs nothing and is a deep habit: 198 times in a single session. If writing an entry takes more thought than that, an agent under load drifts back to a loose file beside the database, and the record quietly stops being the truth. So writing an entry has to be one short command, as easy as adding a line and safe with any text. Looking something up has to beat searching a file.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

We'll replace each session's ledger file with a small database in the same session folder, plus a handful of commands in the package's command line for writing to it and reading from it. The database only ever accepts new entries: it refuses every edit and every delete on its own, whoever asks. Agents write an entry with one short command that stamps the real time and takes any text safely. They read back what is in force, search everything, and print the whole record as plain text whenever a person wants to read it.

Entries

Every entry is one of three kinds, and the kind decides what it has to carry.

  • A decision is something that now governs the work. It always says who decided it: the person or the agent. When the person decided, the entry carries their own words.

  • A finding is something we learned about the product. It always says where it came from: a file and line, a command and what it printed, a page, a test.

  • Progress is where the work stands: what was launched and under which id, on which branch, what a check returned.

A decision or a finding can later be replaced by a new entry that names it — a decision the person changed, a finding that turned out wrong. An entry is in force until something replaces it. The replaced entry stays exactly as it was, readable forever, with a pointer to what replaced it. Progress is never replaced; it just gets older.

The ledger holds nothing else. Questions still waiting on the person stay in the conversation, and lessons about how we work go to the self-improvement pass, as they do today.

Who writes

Every agent in the session writes to the same record: the orchestrator and every subagent it launches. Each entry says who wrote it — the orchestrator, or the subagent's name for its task, such as a lane or a researcher. Today a subagent is forbidden from touching the session's ledger, because a file can be clobbered, so its findings survive only if the orchestrator copies them over from its report. A record that can't be rewritten removes that danger. A subagent writes its findings straight in, with their sources, and its report points at them.

What is in force stays the orchestrator's call. An entry a subagent wrote says so plainly, and when the orchestrator checks a claim and finds it wrong, it replaces it. Nothing changes about verifying what subagents say; the claim is simply never lost.

Writing an entry

We'll add one command per kind: ledger decision, ledger finding, and ledger progress. Each asks only for what its kind has to carry, and every one of them says who is writing. A real finding from the session that shaped this document looks like this: 

pnpm exec seasoned-skills ledger finding --as sqlite-research --source "node -e on Node 22.22" <<'EOF'
node:sqlite prints an ExperimentalWarning on every run on Node 22; Node 24.21 prints none.
EOF

The command answers with the entry's number, kind, and time — #41 finding, 2026-10-14T15:02:11Z — and nothing else. The time comes from the database's clock, never from the agent.

The text only ever arrives on the command's standard input, never as an argument. The shell reads a command line before running it, and inside a double-quoted argument it runs anything written between backticks or inside $( ). That is exactly how a note once merged a pull request it was only quoting. Text fed through a quoted heredoc reaches the command untouched. The hook that already inspects shell commands will refuse a ledger write whose heredoc isn't quoted, so the one way to get it wrong is stopped before anything runs.

▸ Contract The write commands 
ledger decision --as <writer> --by person|agent [--replaces <id>]   < text
ledger finding  --as <writer> --source <where>  [--replaces <id>]   < text
ledger progress --as <writer>                                        < text

  • --as is required on every write, the orchestrator's included (--as orchestrator). Nothing in the environment tells an orchestrator from a subagent: both carry the same CLAUDE_CODE_SESSION_ID, and CLAUDE_CODE_CHILD_SESSION=1 is set in the orchestrator too. A default would record a forgetful subagent as the orchestrator.

  • Empty standard input, or a terminal instead of a pipe, is refused: an entry always has text.

  • The guard hook refuses a Bash command that runs a ledger write with an unquoted heredoc delimiter. Guard hooks that match on command text — the one blocking git stash today — ignore the body of a ledger write's heredoc, so an entry that mentions a forbidden command is recorded rather than refused.

Reading it back

We'll add four ways to read. Three of them cost the same however long the session runs, because consulting the record on day ten must take no more reading than on day one.

  • ledger on its own shows what is in force: every decision still in force, newest first, each with who decided it, who wrote it, and when; then the last ten progress entries; then only a count of the findings, with a reminder to search them. Decisions are the rules of the work and a long session holds dozens, not thousands. Older progress is history. Findings pile up into the hundreds, and the session needs one when a question comes back — and the question carries the words to search for.

  • ledger search <words> searches every entry, in force or not, ranked by how well it matches. Each result is a short excerpt with its number, kind, writer, and time. A replaced entry says “replaced by #N”, so a finding that turned out wrong is never mistaken for a current one.

  • ledger show <number> prints one entry whole, with its source, and its line of replacements both ways: what it replaced and what replaced it.

  • ledger print prints the whole record as plain text, in order, for a person who wants to read it end to end, copy it, or keep it. It is the one read that grows with the session, on purpose: it is the person's way in, not the agent's way back.

▸ Spike Search and what is in force

Proven on a throwaway database under Node 24.21 and 22.22. Search is an FTS5 external-content index over the entry text, fed by an AFTER INSERT trigger, ranked with bm25 and excerpted with snippet; the porter unicode61 tokenizer matches “lanes” on “lane”. In force is a view: a decision or finding with no later entry naming it in replaces. A replacement line is a recursive query over replaces.

The search index is derived data, not the record, and it is the one part a stray command can empty: FTS5's own 'delete' and 'delete-all' commands bypass every trigger, and a virtual table accepts no triggers of its own. A row count cannot see the damage — on an external-content index, count(*) reads the table and still reported 2 rows after 'delete-all' emptied the index — but FTS5's integrity-check with a rank of 1 fails on it. So every search runs that check first and rebuilds the index when it fails. The record itself is never at risk from this.

▸ Schema An entry

One table, STRICT. The integer primary key is the only unique constraint: any other UNIQUE column would open a way for INSERT OR REPLACE to delete a row without firing a delete guard, which the spike showed with a unique replaces column. Rules that need uniqueness are enforced by BEFORE INSERT triggers instead. 

entries(
  id          integer primary key,
  kind        text  -- 'decision' | 'finding' | 'progress'
  body        text  -- the entry, verbatim as written
  decided_by  text  -- 'person' | 'agent'; required on a decision, absent otherwise
  source      text  -- required on a finding, absent otherwise
  written_by  text  -- 'orchestrator', or the subagent's task name
  replaces    integer references entries(id)
  written_at  text  -- UTC, from the database clock, never from the writer
)

Refused on insert: a replaces pointing at a progress entry, at an entry of another kind, at an entry that does not exist yet, or at an entry something already replaced. In force means: a decision or finding no later entry replaces.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • No jobs, tasks, or statuses. This is a ledger for context, not a project management tool. The record is one flat stream per conversation: it never groups entries into pieces of work, never tracks what is open or done, and never asks anyone to start or close anything. A decision from an earlier piece of work stays in force until something replaces it, and its time and writer show how old it is.
