Shaping document

Ledger database

Each session's ledger becomes a database that refuses every edit and every delete, so what was decided, learned, and done comes back exactly as it was written.

Not built yet Built

Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

Late in August, deep into a long shaping session, the person running it told the agent that the conversation was about to be compacted: summarized, to free room for more work, with everything not in the summary gone from the agent's memory. The agent had been keeping a ledger all along: the running file where a session writes down what was decided, what it learned, and where the work stands, so it can find its way back after a compaction. To get ready, the agent rewrote that ledger into a short summary of the current state, and in doing so deleted the history it had built up over the session.

The person also named why this is the worst possible moment to rewrite anything. An agent whose memory is nearly full is at its least capable, so the rewrite is a summary made by the weakest version of the agent, under exactly the strain the ledger exists to protect against. Whatever it drops is gone for good once the compaction lands. Nothing in the file stopped the rewrite, and nothing in it showed what had been lost.

Today's way, and where it breaks

Today each session, meaning one conversation with Claude Code, keeps its ledger as a plain text file in its own folder. Agents add to it one line at a time, by typing commands or editing the file, and read it the same way. In one session we followed from start to finish, the ledger was written 198 times and only ever read by its last few lines. It holds three kinds of things: what the person decided, what the session learned about the product while researching it, and where the work stands: what is running, on which branch, with which result.

It breaks in four places.

  • Anything can rewrite it. A file accepts any edit, so history gets replaced, as in the story above. Ledgers also keep a short summary of where things stand at the top, meant to be kept current, and it goes stale: one ledger reached 1,484 lines while its top section still described work from five days earlier.

  • Writing it can do damage. When an entry goes in through the program that runs the agent's commands, that program can mistake text for an order. One entry listed four next steps as a reminder, among them merging a change into the shared code without anyone's approval. The computer tried to run all four. They failed only because of where the agent happened to be working at that moment, and nothing merged.

  • Its times are made up. Agents type each entry's time from memory, and the times drift: minutes, hours, and once by two days. Writing the rule down did not help.

  • Finding anything gets more expensive every day. A finding from research sits somewhere in a long log, between launch notes and test results. Getting it back means searching a file that keeps growing, and reading the file costs more of the agent's memory (its context window) the longer the session runs.

To cope, agents restate rules inside the ledger, read it in pieces once it grows too big to open in one go, and repair it by hand when a write goes wrong. None of it makes the record trustworthy again.

The outcome test

  1. Nothing written can be changed or removed through the database. Every edit or delete is refused by the database itself, not by a rule the agent is asked to follow.

  2. What we learn about the product stays learned. A finding from research — how a piece of functionality behaves, why the code is the way it is, a premise that turned out false — is recorded the moment we have it, with where it came from. When the same question comes up later in the effort, the session finds the finding instead of researching it again.

  3. Whenever the session consults the record, it gets back exactly what was written. What the person decided, what the session learned, and where the work stands each come back in their original words, stamped with the real time they were written. What is still in force is shown apart from what was later replaced, and the replaced entries stay readable.

  4. The history never gets in the way. However long the session runs, the agent reads only what still applies, and finds anything else by searching.

Nobody makes the session study the whole record at a fixed moment. Agents reach for the ledger when a question needs it, and whenever they do, the record has to be there, whole and quick to search.

Why now

Two recent changes raised the stakes. Ledgers moved out of a temporary folder the computer could wipe and into each project's own session folder, so the file now survives. Compaction now happens on its own, whenever the agent's memory fills, rather than when someone announces it. There is no longer a moment to prepare, and what the session wrote down along the way is all it gets back. The ledger is now the one record every long session leans on, and the remaining question is whether it still says what was written. The payoff is time: every lost or doubtful entry is research done twice, or a session spent working out again where things stood.

The big hire and the little hires

The big hire is the person who upgrades the package in a project (seasoned-skills, the shared instructions and tools our projects install): from then on, every session there keeps its ledger in the database. To make that switch they must lose nothing they have today, and one thing they have today is a ledger anyone can open. People read ledgers directly, copy them, and have rebuilt a lost one by hand. So the whole record has to stay readable as plain text, by a person as easily as by an agent.

The little hires are the agents, every time they write an entry or look something up, and this is where the switch really gets decided. Adding a line to a file costs nothing and is a deep habit: 198 times in a single session. If writing an entry takes more thought than that, an agent under load drifts back to a loose file beside the database, and the record quietly stops being the truth. So writing an entry has to be one short command, as easy as adding a line and safe with any text. Looking something up has to beat searching a file.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

We'll replace each session's ledger file with a small database in the same session folder, plus a handful of commands in the package's command line for writing to it and reading from it. The database only ever accepts new entries: it refuses every edit and every delete on its own, whoever asks. Agents write an entry with one short command that stamps the real time and takes any text safely. They read back what is in force, search everything, and print the whole record as plain text whenever a person wants to read it.

The record

We'll give each conversation one record: a single database file in its session folder, the same folder where the ledger file lives today, so it survives a reboot and is cleaned up with the folder when Claude Code deletes the conversation's saved history. The first write creates it. Every agent in the conversation reaches the same record on its own, whichever copy of this project's code it is working in.

We'll build it on the database that comes inside Node, the software the package already runs on, so nothing new gets installed. Projects on an early release of Node 22 will need to update it for the ledger; every other command keeps working until they do.

▸ Contract The file, the runtime, and several writers at once

  • The record lives at .sessions/<session id>/ledger.db in the main checkout, resolved exactly as session-folder resolves the folder (CLAUDE_CODE_SESSION_ID, then git rev-parse --git-common-dir for the main checkout). Outside a Claude Code session every write fails the way session-folder does, and a read needs --session (see the read commands). The folder sweep already removes everything in the folder, the database's -wal and -shm companions included, so it needs no change, as long as the ledger commands create the folder through sessionFolder() itself: the sweep keeps forever any folder without the .projects file only that function writes (src/sessions/folders.ts).

  • node:sqlite needs no flag from Node 22.13 on, but FTS5 arrives in it only with Node 22.16: Node 22.13 to 22.15 bundle an SQLite built without it, and creating the search index there fails with no such module: fts5. Node 22 prints ExperimentalWarning: SQLite is an experimental feature on every run; Node 24 prints none. FTS5, JSON functions, and STRICT tables work on both from 22.16. engines.node becomes >=22.16.0, up from >=22.0.0. A new warning filter replaces Node's warning listener with one that drops only the SQLite experimental warning and prints everything else. It is installed in bin/seasoned-skills.js before the command line is loaded with a dynamic import(), so it is in place before anything imports node:sqlite. The ledger commands import node:sqlite lazily, inside their own actions, never from src/cli/program.ts: engines is only advisory, and on Node 22.0 to 22.12 a static import breaks every command, sync in prepare and the session-end hook included. Before anything else, every ledger command checks that node:sqlite loads and creates an FTS5 table in memory. On a Node where either fails, only ledger fails, with “The ledger needs Node 22.16 or later.”, before it creates a folder or a file, and the compaction hook prints nothing.

  • Every connection sets a 5-second PRAGMA busy_timeout (the pragma also works on Node 22 versions older than the timeout option). Agents write at the same moment all the time, each command on its own connection, and without the wait most of those writes fail with database is locked. WAL mode lets reads run while a write is open.

Entries

Every entry is one of three kinds, and the kind decides what it has to carry.

  • A decision is something that now governs the work. It always says who decided it: the person or the agent. When the person decided, the entry carries their own words.

  • A finding is something we learned about the product. It always says where it came from: a file and line, a command and what it printed, a page, a test.

  • Progress is where the work stands: what was launched and under which id, on which branch, what a check returned.

A decision or a finding can later be replaced by a new entry that names it: a decision the person changed, a finding that turned out wrong. An entry is in force until something replaces it. The replaced entry stays exactly as it was, readable forever, with a pointer to what replaced it. Progress is never replaced; it just gets older.

The ledger holds nothing else. Questions still waiting on the person stay in the conversation. Lessons about how we work stay in the conversation too, until the review we run at the end of every task picks them up; that review already reads the whole conversation. This is a change: today's rule puts those lessons in the ledger.

▸ Schema An entry

One table, STRICT. The integer primary key is the only unique constraint: any other UNIQUE column would open a way for INSERT OR REPLACE to delete a row without firing a delete guard (a unique replaces column would let one replacement silently wipe out another). Rules that need uniqueness are enforced by BEFORE INSERT triggers instead. 

entries(
  id          integer primary key,
  kind        text  -- 'decision' | 'finding' | 'progress'
  body        text  -- the entry, verbatim as written
  decided_by  text  -- 'person' | 'agent'; required on a decision, absent otherwise
  source      text  -- required on a finding, absent otherwise
  written_by  text  -- 'orchestrator', or the subagent's task name
  replaces    integer references entries(id)
  written_at  text  -- UTC, from the database clock; our commands never take a time
)

Refused on insert: a replaces pointing at a progress entry, at an entry of another kind, at an entry that does not exist yet, or at an entry something already replaced. In force means: a decision or finding no later entry replaces.

The guards

We'll set the database to refuse every change and every removal of an entry itself, whoever asks and through whatever tool: our own commands, a stray script, or someone typing into the database by hand. Every time our issue reports show an agent damaging a ledger, it was an accident under load: a rewrite before compaction, a note the computer ran as commands. Each took one ordinary command against a text file. Against a database none of them can happen by accident: there is no file to overwrite with one careless command, and an edit or a delete is refused. Getting around the guards takes deliberate steps nobody takes by mistake, and we won't build anything to catch those (see the no-gos).

▸ Schema What the guards refuse, and what escapes them

Three BEFORE triggers, each ending in RAISE(ABORT, …):

  • BEFORE UPDATE refuses every edit, upserts (ON CONFLICT DO UPDATE) included.

  • BEFORE DELETE refuses every delete, whole-table included.

  • BEFORE INSERT … WHEN EXISTS (an entry with NEW.id) refuses INSERT OR REPLACE and REPLACE INTO. Without it, a replace silently swaps the row: its implicit delete fires no delete trigger while recursive_triggers is off, which is SQLite's default and a per-connection setting nobody else's connection will turn on. This is also why the primary key is the only unique constraint.

What escapes, deliberately out of scope: DROP TRIGGER, DROP TABLE, renaming and recreating the table, editing the schema through PRAGMA writable_schema (refused under Node 24's defensive default; allowed on Node 22 and by the sqlite3 command line), and deleting the file.

Who writes

We'll let every agent in the session write to the same record: the orchestrator (the main agent the person talks to, which hands out pieces of the work) and every subagent it launches (a helper agent with one task, such as building one piece in its own copy of the code, which we call a lane, or researching a question). Each entry says who wrote it: the orchestrator, or the subagent's name for its task. Today a subagent is forbidden from writing to the session's ledger, because a file can be overwritten by accident, so its findings reach the session's ledger only if the orchestrator copies them over from its report. A record that can't be rewritten removes that danger. A subagent writes its findings straight in, with their sources, and its report points at them.

Subagents write findings and nothing else. Decisions and progress belong to the orchestrator. A decision governs the whole session, so it comes from the person or from the orchestrator's own judgment, never from one lane's choice; when a lane's choice matters, the orchestrator records it after reading the report. Progress is recorded only once its result has been read, and the orchestrator is the one who reads and checks what subagents report. A lane's working notes stay in its report.

What is in force stays the orchestrator's call. An entry a subagent wrote says so plainly, and when the orchestrator checks a claim and finds it wrong, it replaces it. Nothing changes about verifying what subagents say; the claim is simply never lost.

Writing an entry

We'll add one command per kind: ledger decision, ledger finding, and ledger progress. Each asks only for what its kind has to carry, and every one of them says who is writing. A real finding from the session that shaped this document looks like this: 

pnpm exec seasoned-skills ledger finding --as sqlite-research --source 'node -e on Node 22.22' <<'ENTRY'
node:sqlite prints an ExperimentalWarning on every run on Node 22; Node 24.21 prints none.
ENTRY

The command answers with the entry's number, kind, and time, such as #61 finding, 2026-10-14 15:12:40 -03:00, and nothing else. The time comes from the database's clock, never from the agent.

We'll take the text of an entry in a way that never lets the computer run any of it as a command, however it is written. A new check on every command agents run will refuse a ledger write that skips that protection, so a note that quotes a command can never run it again.

▸ Contract The write commands 
ledger decision --as <writer> --by person|agent [--replaces <id>]   < text
ledger finding  --as <writer> --source <where>  [--replaces <id>]   < text
ledger progress --as <writer>                                        < text

  • The text arrives only on standard input, never as an argument. The shell expands a command line before running it, and inside a double-quoted argument it runs anything between backticks or inside $( ). An unquoted heredoc expands the same way, which is how the entry in issue #418 ran four commands it was only quoting. A quoted heredoc reaches the command untouched. Every ledger write uses the same one, <<'ENTRY', so the guard hook and the standing instructions name a single form, and an entry's text can hold any line except one that is exactly ENTRY.

  • --as is required on every write, the orchestrator's included (--as orchestrator). Nothing in the environment tells an orchestrator from a subagent: both carry the same CLAUDE_CODE_SESSION_ID, and CLAUDE_CODE_CHILD_SESSION=1 is set in the orchestrator too. A default would record a forgetful subagent as the orchestrator. ledger decision and ledger progress refuse any writer but orchestrator, so a subagent that reaches for them by mistake is stopped; only ledger finding takes a subagent's name. Any writer may replace a finding with a finding, so a subagent that disproves one records the correction as its replacement, with the source that disproved it. What is in force stays the orchestrator's call: when it checks the correction and finds it wrong, it replaces it in turn, and the chain shows all three.

  • Every ledger command runs from the project's root or one of its worktrees where pnpm install has run, as session-folder already does, so the conversation has one record even when a lane also works in another repository: that repository's checkout would resolve to a different session folder. An agent in a plain worktree with no installed dependencies runs its ledger commands from the project's root.

  • Empty or whitespace-only standard input, or a terminal instead of a pipe, is refused: an entry always has text. The text is stored exactly as it arrives, less the one trailing newline the heredoc adds. --replaces takes a number with or without a leading #, and the standing instructions teach the bare number.

  • A new managed PreToolUse hook on Bash (timeout 10 seconds, like the stash hook), beside runtime/hooks/block-git-stash.sh, today the only hook that reads Bash commands. A ledger write is a command whose own words, outside quotes and heredoc bodies, run the package's binary, in any form (pnpm exec seasoned-skills, npx, node bin/seasoned-skills.js), with ledger decision, finding, or progress; a commit message or PR body that only mentions one is not a write. The hook refuses a second ledger write in the same Bash command, and anything after the closing ENTRY line: a write may be preceded by cd … && but must end the command, and its line ends at <<'ENTRY'. That also closes the last way an entry could run: a line in the text that is exactly ENTRY ends the heredoc early, the lines after it become commands, and the hook sees text after the closing line and refuses. It refuses a write in a command where any heredoc never closes, since shells disagree about where an unclosed heredoc's text ends, and some would read the entry into it and expand it. It refuses a write whose text does not arrive through <<'ENTRY', which also refuses echo … | and a missing heredoc. A request for help, --help or -h where it is no option's value, writes nothing, so it needs no heredoc. It refuses a --source holding a backtick or a $ unless it is single-quoted, since a source is often a command and what it printed, and inside double quotes the shell would run it or swap in a variable's value. And it refuses any ledger command with an unquoted word starting with #: the shell reads --replaces #47 <<'ENTRY' as a comment from # on, the heredoc disappears, and every line of the entry runs as a command, exactly the #418 failure.

  • Guard hooks that match on command text, the stash hook included, skip a ledger write's body: the lines after the one holding <<'ENTRY', up to the line ENTRY. The line holding <<'ENTRY' is checked as usual, so … <<'ENTRY' && git stash is still refused. Only a ledger write's heredoc is skipped, never any other. An entry that mentions a forbidden command is recorded rather than refused. Hooks a project registers on its own are outside the package's reach and keep reading the whole command.

  • Both hooks need the same reading of a command: which words sit outside quotes and heredoc bodies, across && chains and $( ). That reading lives in one small Python helper shipped beside them in runtime/hooks/, as today's hooks already run inline python3. It is never a seasoned-skills command: starting the package through pnpm exec costs about a quarter of a second, and these hooks run before every Bash command any agent sends.

  • The ledger commands are the command line's first nested commands. The reference test in tests/unit/reference-docs.test.ts reads program.commands, their flags, and their positional arguments one level deep, so it would never notice an undocumented ledger search, its words, or its flags. It will walk the command tree to any depth, checking each command's flags and positional arguments under a heading that carries its full name, before the ledger commands land. The golden command-line test (tests/golden/cli-surface.test.ts) pins only top-level names and descriptions, and gets the same walk.

Reading it back

We'll add four ways to read. Three of them keep the history out of the agent's way: it reads only what still applies, and searches for the rest.

  • ledger on its own shows what is in force: every decision still in force, newest first, each with who decided it, who wrote it, and when; then the last ten progress entries; then only a count of the findings, with a reminder to search them. Decisions are the rules of the work and a long session holds dozens, not thousands. Older progress is history. Findings pile up into the hundreds, and the session only needs one when its question comes back. That question carries the words to search for, so a count and a reminder are enough here.

  • ledger search <words> searches every entry, in force or not, ranked by how well it matches. Each result is a short excerpt with its number, kind, source, writer, and time. A replaced entry says “replaced by #N”, so a finding that turned out wrong is never mistaken for a current one.

  • ledger show <number> prints one entry whole, with its source, and its line of replacements both ways: what it replaced and what replaced it.

  • ledger print prints the whole record as plain text, in order, for a person who wants to read it end to end, copy it, or keep it, and for the review at the end of a task, which reads everything on purpose. Every replaced entry says what replaced it, and every replacement says what it replaced. It is the one read that grows with the session, and the agent never uses it to find its way back.

▸ Contract The read commands 
ledger                    [--session <id>] [--hook]
ledger search <words...>  [--session <id>]
ledger show <number>      [--session <id>]
ledger print              [--session <id>]

  • --session <id> names a folder under .sessions/ and wins over the environment, so a person in their own terminal, or an agent in today's session, can read today's record or yesterday's. Without it, a read uses the current session, and outside a Claude Code session it fails the way session-folder does. The id is checked against the session-id pattern in src/sessions/folders.ts, so nothing like ../ gets through. Reads resolve the folder without creating it, unlike sessionFolder(), which always creates one; a mistyped id must never leave behind a folder the sweep would keep forever. Writes never take --session. Each read command declares its own --session, and positional options are turned on for both the program and ledger, since Commander otherwise hands a subcommand's flag to the parent (tried on Commander 15: with ledger alone, ledger search foo --session X read the current record). ledger's own --session and --hook are refused when a subcommand follows them, so ledger --session X decision never writes to the current record unnoticed. A side effect: seasoned-skills <command> --version stops working; seasoned-skills --version still does.

  • A read with no record yet prints “No ledger yet in this session.” and exits 0. show takes a number with or without a leading #.

  • ledger shows only what is in force. Replaced entries never appear in it; search, show, and print mark them. ledger prints progress entries whole; only the compaction hook shortens them. Wherever text is shortened, a search excerpt or a hook line, it ends in an ellipsis and is never reworded, and the whole entry is one show away.

  • Times are stored in UTC and shown in the machine's local time: the full stamp with its offset where one entry is printed; in the lists, the time of day for today's entries and the date and time for older ones, so a decision from five days ago shows its age.

  • Search takes plain words, never FTS5 syntax. Every argument is split on whitespace, so "busy timeout" is two words, never a phrase, and each word is quoted as a plain term, so node:sqlite, #418, a hyphen, or an uppercase OR is just text. It covers each entry's text and its source. The terms are joined with OR; results are ordered by how many of the words they match, then newest first, so a lane relaunched under a new task id finds its latest launch on top. Recency stands in for bm25 here: in a ledger, the newest match is the one that matters. It prints the 20 best matches, then “N more not shown”.

  • --hook is the compaction hook's mode, like sweep --hook: it reads the hook's JSON payload from standard input, takes the session from its session_id, fits the view under the hook's budget, prints nothing when there is no record, and always exits 0.

  • Cost means how much text the agent has to read. ledger prints the decisions in force, the last ten progress entries, and one line about findings, and search prints at most 20 excerpts, whatever the size of the record.

▸ Schema Search and what is in force

Search is an FTS5 external-content index over the entry text and source, fed by an AFTER INSERT trigger, and excerpted with snippet; results are ordered as the read commands say. The porter unicode61 tokenizer matches “lanes” on “lane”. In force is a view: a decision or finding with no later entry naming it in replaces. A replacement line is a recursive query over replaces.

The search index is derived data, not the record, and it is the one part a stray command can empty: FTS5's own 'delete' and 'delete-all' commands bypass every trigger, and a virtual table accepts no triggers of its own. A row count cannot see the damage: on an external-content index, count(*) reads the table, so it keeps counting every entry after the index is emptied. FTS5's integrity-check with a rank of 1 does fail on it. So every search runs that check first and rebuilds the index when it fails. The check is itself a write, so it runs only when the write lock is free at once; while another connection holds a write open, the search reads the index as it is. The record itself is never at risk from this.

After a compaction

We'll add a hook, a small script Claude Code runs on its own at set moments, that runs every time a conversation is compacted and puts the decisions in force back in front of the agent, word for word, before it takes its next step. Nobody has to remember to look: in the one session we followed end to end, the agent never opened its ledger after any of five compactions. It found its way back from the summary alone. A summary paraphrases, and our issue reports show what happens next: the paraphrase of a decision becomes the decision. With the hook, the person's decisions come back in the person's own words every time.

The hook only shows; it never makes the agent read anything else. Searching for findings stays the agent's call, when a question comes back. When the conversation has no record yet, the hook prints nothing, and it can never stop a compaction.

▸ Contract The compaction hook

  • A managed SessionStart hook with the compact matcher (timeout 10 seconds), shipped in runtime/hooks/ and registered beside the session-end hook. Like the session-end hook, it starts with cd "$CLAUDE_PROJECT_DIR" and sets COREPACK_ENABLE_DOWNLOAD_PROMPT=0, so Corepack's prompt can never eat the payload, then pipes its payload to pnpm exec seasoned-skills ledger --hook, which takes the session from the payload rather than trusting a hook process's environment. It prints the in-force view as plain text, which Claude Code adds to the agent's context. It always exits 0.

  • Claude Code caps what a hook can add at 10,000 characters; past that it saves the text to a file and shows only a 2,000-character preview. So the hook prints the same view as ledger, fitted under 9,500 characters. The findings line and the last ten progress entries, each cut to its first line and 200 characters, are set aside first. Decisions in force fill the rest, newest first and only whole, stopping at the first one that doesn't fit, followed by “N older decisions in force: run pnpm exec seasoned-skills ledger”. A decision is never cut mid-text, and none is skipped to fit an older one. The one exception is a single decision longer than all the room left for decisions once progress and the findings line are set aside: it appears as one line, “#N is too long for this view: run pnpm exec seasoned-skills ledger show N”, and the fitting goes on.

  • Claude Code's hooks documentation does not say whether SessionStart fires when a subagent compacts. The hook is built for the orchestrator, where the person's decisions live; a subagent can always run ledger itself.

What changes in the way we work

We'll rewrite the rules agents follow along with the record, so no agent keeps writing a markdown file out of habit.

  • The rule about ledgers in each project's standing instructions stops saying “keep a ledger file with all the durable lessons and state” and says to keep the session's ledger with the ledger commands, run from the project's root or one of its worktrees. The advice after it stays, reworded: after a compaction the decisions in force are already in front of the agent, and going back to the real sources before the next step still applies. It also says that a session older than the upgrade may have a markdown ledger beside the record, to be read as history.

  • The ledger part of the orchestrator's playbook loses the rules for keeping a summary at the top of the file, moving old summaries to an archive, and reading the file in pieces. It gains short rules for what to record and when: a finding the moment it is learned, with its source; a decision the moment it is made, in the person's own words when it is theirs; progress only after its result has been read, never written in the same step as the command that produces it; and a change of mind always as a replacement.

  • Instructions to subagents stop forbidding them from writing to the ledger, and subagents stop keeping ledgers of their own. Each one gives the subagent its --as name and tells it to record its findings with their sources.

  • Smaller mentions follow: the agent finds a launched task's number by searching the record; when the person rules on review comments, those rulings are recorded as decisions; the end-of-task review writes ledger print to a file in the session folder and reads it the way it reads the conversation, in slices, never whole into its context, and no longer looks for ledgers kept by subagents; and the lightweight mode for small fixes still keeps no ledger.

  • The pages people read describe the ledger as it now is: the way of working, running a session, the command reference, and the list of files the package manages.

Walkthrough

The same long shaping session from the story, replayed with the record in place.

  1. Early in the session, the person settles how the problem is framed. The agent records it as a decision by the person, in the person's words, and the command answers with the entry's number and the real time. A subagent sent to research how a piece of the product behaves records what it found, with the file and line it found it in, and its report back points at that entry.

  2. Hours later the person changes their mind about one of those decisions. The agent records the new decision as replacing the old one. The old entry is still there, word for word, now marked as replaced by the new one.

  3. The agent's memory fills. Nobody announces the compaction, and nobody needs to: there is nothing to tidy up beforehand. Had the agent still tried to boil the record down to a summary, the database would have refused to delete or edit a single entry. A summary it wrote would only have become one more entry, after all the others.

  4. The compaction lands. Before the agent takes its next step, the decisions in force appear in front of it, newest first, each in the words it was written in, with who decided it and when. The replaced decision is not among them. The agent works from the person's rulings, not from the summary's paraphrase of them.

  5. Later, a question the subagent already answered comes back. The agent searches the record for a few words from the question, finds the finding with its source, and goes on. Nobody researches it twice, and none of the day's history got in the way.

  6. At the end of the day the person prints the record and reads it from top to bottom: every decision, every finding, every step of progress, in the order they happened, with the real times. The question from August has nothing left to ask about: the history is all there.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • No jobs, tasks, or statuses. This is a ledger that helps the agent remember, not a project management tool. The record is one flat stream per conversation: it never groups entries into pieces of work, never tracks what is open or done, and never asks anyone to start or close anything. A decision from an earlier piece of work stays in force until something replaces it, and its time and writer show how old it is.
  • No defense against deliberate tampering. Someone who drops the database's guards on purpose, or deletes the file, can do it, and we won't build any tamper detection to catch it. The guards exist for the accidents our issue reports actually show.
  • No import of old markdown ledgers. A markdown ledger has no kinds, no sources, and no reliable times, so an importer would have to invent all three, and the record would start its life with made-up sources and times. A session that is running when its project upgrades keeps its markdown file where it is, readable as history, and writes every new entry to the database. Session folders go away when Claude Code deletes the conversation's saved history, so these old files disappear on their own.

Build the ledger database: each session's ledger becomes a database that refuses every edit and every delete, so what was decided, learned, and done comes back exactly as it was written.
