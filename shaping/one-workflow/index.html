Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

One person runs several products, and over the last years built a single way of working across all of them: standing instructions, step-by-step guides for recurring work, and small tools, all aimed at one goal — AI agents doing all the work, from pulling requirements out of meetings and out of the running product’s behavior, through framing and shaping, to building, releasing, and watching what ships. Not every step is fully theirs yet, but no person builds anything by hand anymore. Each project keeps its own hand-made copy of that way of working. On the day this project was framed, an agent working in one repository made a one-line mistake that another project’s instructions had explicitly warned against for weeks — the warning simply never traveled. That is the pattern: every lesson is learned once but taught to only one project, and the person who maintains all the copies is the only bridge between them.

Today's way, and where it breaks

The way of working spreads by hand: when a piece of it improves in one project, someone must remember it exists elsewhere, copy it over, and adapt it — three times, for every improvement. In practice that rarely happens, so the copies drift. Measured on the day of framing: of the nine guides all active projects share, exactly one was still identical everywhere — every other copy had quietly forked. Starting a new project means copying from whichever existing project feels most current and pruning what does not apply, with no way to tell later which parts are behind.

The outcome test

Take any of our active projects, remove every hand-maintained piece of the way of working, and install this package in its place: the project works exactly as it did before — nothing lost, and everything that was particular to that project preserved through its own configuration. From that day on, staying current means upgrading a version, and a lesson written once reaches every project on its next upgrade.

Why now

Agents now do the work end to end, so the way of working — not any single product’s code — has become the company’s biggest compounding asset, and it is the one asset currently maintained by hand in parallel copies. Every week of three-way drift makes the eventual reunification harder, and the next project to adopt the workflow should cost an install, not an afternoon of copying and pruning.

The big hire and the little hires

The big hire is deliberate and total: a project adopts by handing its whole way of working to the package — all or nothing. The install takes over the project’s standing instructions, its guides, and its supporting tools from day one; there is no partial adoption, and that is a promise, not a limitation.

The little hires are the upgrades: each new version quietly bringing every project the newest lessons, and each newly-learned lesson written once, in one place, with certainty it will reach everywhere.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

The whole way of working — the standing instructions, every guide, the small supporting tools — moves into one published package that any project can install. A project adopts it by installing the package and filling in one configuration file; from then on, staying current means upgrading a version.

The heart of the idea: nothing the package produces is ever written by hand inside a project again. From the configuration plus the package’s own content, the install generates every instruction file the project’s agents read. A project commits only what is genuinely its own — the configuration file and its own content, kept wherever it prefers. Everything generated is disposable and rebuilt at will.

▸ Contract What the install materializes, and what a project commits

Generated and gitignored: the project’s agent instructions file, every skill the package ships, the hooks, and the supporting scripts. Committed by the project: seasoned-skills.config.ts at the repo root, plus the project-owned content files it points at (project facts, custom instructions, design-system vocabulary). Published: a public npm package under an MIT license — the package carries only our own prose and machinery.

The package shares the agent-configuration folder with the project; it never owns it. A project keeps its own committed skills alongside the generated ones and its own additions to the agent settings. The tool manages exactly two footprints surgically: in the ignore file, a script checks that every path the package generates is ignored and adds only the missing entries, never removing or reordering anything the project put there; in the settings file, the tool enforces the values of the keys the workflow depends on and leaves every other key untouched. Check-and-edit, idempotent, in both files.

Because instructions are generated, differences between projects stop being forks and become configuration. Divergence comes in two kinds: drift — the same rule aging differently in each copy — which generation eliminates; and legitimate difference — a team repository versus a solo one, a stack without a given technology, a practice one project is not ready for — which the configuration expresses. Giving legitimate difference a home leaves illegitimate difference nowhere to hide.

The workflow is organized in layers a project enables when it is ready for them. Enabling a layer composes it into everything else: every generated instruction that should mention it starts mentioning it, and disabling it removes every trace, so no instruction ever points at a practice the project does not run. One discipline keeps this honest: a configuration option exists only where a genuine, durable difference between projects demands one — our own active projects’ configurations are the tested combinations, and an option no project uses gets deleted.

Concretely, the package has five layers. The doctrine layer is the standing instruction file every working session reads first. The practice skills are the guides for how work is done — orchestrating agents, testing, reviewing, shaping, releasing — and every one of them comes with the workflow, whole, because every project we run uses all of them. The stack layer — the guides tied to one specific technology stack — is the only optional one: a project declares its stack, or doesn’t. The deterministic code layer is the small supporting tools: the scripts, the hooks, and each project’s runtime settings. And the corpus machinery builds, on each person’s own machine, the reference library the shaping practice reads from. The configuration decides which layers materialize — and a skill enters the package only when a second project needs it, never on the hope that one someday might.

▸ Contract Rulings — how work flows

From the doctrine adjudication: agent merges to the base branch during a goal are off by default and opt-in per project; everything else unified with no option — checkouts never leave the default branch (documentation work uses an unprovisioned worktree), questionnaires only when the user may be away, browser verification for any work that could affect user-facing behavior, the reference-privacy rule everywhere and not toggleable, the leaner one-question rule, the responsive bar’s stack-neutral core with framework-coupled lines injected from project content, and the quality bar’s design-system clause restored. Backwards compatibility is a confidence judgment, never a blanket ban: the generated rule reads “do not add backwards compatibility unless you are 100% confident it is necessary”, and a project’s real compatibility contracts — a GA API surface’s consumers, live integrations, frozen legacy surfaces — are named from its own content, so the same rule serves greenfield and long-lived projects alike.

From the skills adjudication: what an agent does with breakage it discovers outside its task’s scope is the second option. In every project, every finding gets an explicit disposition the moment it is confirmed — nothing parked undecided, nothing dropped. But only projects that opt in let agents fix discovered breakage autonomously, under a codified Definition of Broken — a failing gate, a reproducible runtime failure, a violation of written doctrine; never a judgment call. Projects not ready for that level of autonomy get the conservative default: out-of-scope findings are banked with evidence and adjudicated with the user. In both modes, an out-of-scope fix executes in its own dedicated pass, never inline in the lane that found it — that is what keeps lanes convergent and review rounds terminating.

Also from the skills adjudication, no option: a pull request opens as a draft the moment the fast gates pass — so continuous integration overlaps with local verification — and flips to ready for review only after the full pre-merge pipeline completes: builder claims verified, full gates green, the adversarial code-review audit done, and a ruling on every confirmed finding. Small diffs are not exempt from the pipeline; they simply overlap it. Paid auto-reviewers are the consuming repository’s concern: configure them to ignore drafts.

Long gates belong to the orchestrator, no option: a builder’s charter ends at commit — or commit and push — and stops there, with only the fast, cheap checks (lint, type-checking the affected files) run in the builder’s own foreground. The orchestrator runs the full gates itself as its own background shells and owns push, pull request, and merge. This is a structural fix, not an exhortation: instructing builders to run a long suite in the foreground does not survive contact with builders, who background the command and end their turn stalled.

The third option: how a branch reaches the mainline, and with it how a pushed branch syncs with its base — one setting, because the sync strategy follows from the merge strategy. A repository that merges pull requests with a merge commit keeps its branch history linear by syncing lanes with rebase, and carries the discipline that makes rewriting pushed history safe: patch-identity verification and post-rebase reconciliation. A repository that squash-merges syncs every pushed branch by merging the base in and never rewrites pushed commits — the branch’s intermediate history vanishes at the squash, so merge commits cost nothing. Each mode weaves in only its own discipline; no project carries both.

Long-lived processes, no option: every process a lane needs beyond a single turn — a development server, a worker — runs as its own harness background task, never forked with & inside another task’s shell, and every lane process is swept at session end. The double-fork detachment helper one project grew for this is judged a workaround for an older harness and is retired, not shipped; the migration verifies current harness behavior as its closing check.

A continuous-integration watch is a completion signal only, no option: its exit code is never the verdict — the watch command has reported success on genuinely failed runs — and the verdict comes from a fresh direct read of the check states after the watch returns, before anything acts on it.

▸ Contract Rulings — testing discipline

The full end-to-end suite is continuous integration’s job, never a local step, no option: locally a lane runs the specs judged related to the change — related by the change’s blast radius, not literally the specs of the files touched — and the full-suite verdict comes from the integration run on the draft pull request, read fresh.

The route-coverage register, no option — one rule with a brownfield on-ramp: a new surface and the spec that reaches it land in the same change, and the register of unreached surfaces stays empty. When the coverage gate is installed into a project that already has unreached surfaces, the install seeds the register with them; it only ever shrinks, and once empty it is held empty forever. “No spec yet” is never a rationale for exclusion.

Specs never assert one-shot flash messages, no option: their delivery rests on a global no-prefetch property any future change can silently break, failing every such assertion at once. Specs assert the destination and the re-navigated state instead.

No cap on concurrent suites, no option: the orchestrator owns every long gate run, so it schedules heavy suites by judgment when lanes pile up, and a contention-shaped failure — connection exhaustion, timeouts under load — is re-run alone before anyone treats it as a defect. A machine’s real capacity limits are that project’s own facts, not package doctrine.

▸ Contract Rulings — skills in practice

The design-system guide is generated in two parts: the package’s standard guidelines — the design doctrine every project shares, such as token discipline, the typography tiers, the closed status vocabulary, the responsive canon, and the shape of a confirm — woven together with the project’s own design-system guidelines from its content files: its palette, its component library, and its concrete idioms. How a specific idiom renders — how a status presents on a phone, for instance — is adjudicated inside the project’s own guidelines, within the standard doctrine’s bounds.

Browser hygiene splits by audience, no option: the lane-side discipline — one session for the whole run, named after the lane, closed before reporting — lives in the browser skill, and the orchestrator-side discipline — a reported close is not evidence the processes died, sweep to zero between waves, a gate that turns flaky while browser work is in flight is a leak suspect before it is a product bug — lives in the orchestration skill, because the orchestrator rarely loads the browser skill. The never-pattern-kill rule is embodied, not repeated: the package ships two sweep tools — a browser sweep, and a lane-process orphan sweep that lists and kills processes by lane, wired to run at session end and runnable by hand — and both kill only by exact process id, so every kill passes through a tool that enforces the rule. Lane teardown also kills whatever listens on the lane’s ports, so a worker stack orphaned by a killed run cannot outlive its lane.

Saved browser state — cookies, sessions — always goes to an absolute path in the scratchpad directory, never a relative one, no option: relative paths have landed credential files inside repository checkouts. Every example in the generated skill complies, and stale counter-examples die at generation time because the whole skill is regenerated from the package.

The skill roster ships in two tiers: the core — every practice skill, from orchestration and subagents through shaping, meeting requests, releases, and demo videos — comes with the workflow whole, because every project we run uses all of it; only the stack-coupled skills form a separate layer, keyed by the stack the configuration declares. The layer machinery itself stays composable for the layers still to come — performance optimization, observability — and a practice skill splits out into its own optional layer only when a real consuming project actually runs the workflow without it. One skill dies rather than ships: the standalone idea-grilling skill is absorbed by the shaping practice, which interrogates ideas as a matter of course.

▸ Contract Rulings — runtime and deterministic code

The runtime assumptions the workflow depends on — the model and its effort level, always-on thinking, automatic compaction and memory off, the permission mode defaulting to auto, the status line with its model-demotion alarm — are materialized per project by the command-line tool as deterministic code: generated project-level settings and a generated status-line script, gitignored like every other generated file. Nothing ever writes to a user’s global configuration; personal permission lists and machine-local preferences stay personal. A fresh machine needs nothing beyond installing the package in a project — the workflow’s assumptions travel with the project, not with the machine. The status-line script itself — our own tool, previously maintained on its own — is absorbed into the package outright, so one upgrade updates it everywhere it is materialized.

Worktree provisioning, no option: one TypeScript implementation in the package replaces the three divergent copies, driven entirely by the resource table the project’s configuration declares — which databases, which port bases, which services, which repositories. The lifecycle contract is the part all three copies already agreed on: resources allocated by deterministic hash of the lane name and recorded in a managed environment block that doubles as the idempotency sentinel; setup safe to re-run; teardown that drops only namespaced resources and never touches the branch. The provisioning logic is unit-tested once, in the package — projects stop carrying their own copies of the scripts and of the tests that guard them.

Enforcement gates split three ways, no option: the rule (every surface reachable by a spec, every capability mirrored, every surface demo-seeded) is generated doctrine; the checking code that enforces it is package-generated in the stack layer, since walking a route tree is stack-specific; and the lists the check reads — excused surfaces with written rationales, the shrink-only pending register, the seed manifest — are committed, project-owned files the configuration points at, because they are facts about the project that must survive regeneration. A project on a stack the package does not ship keeps its own playbook and its own checker scripts as project content, and the generated instructions point at them exactly as they point at package-generated ones — a stack layer earns packaging when a second project shares the stack, and not before.

▸ Contract Rulings — the stack layer

The database mutability stance is the stack layer’s deepest option, with exactly two tested values: append-only, zero exceptions — insert is the only write the application ever performs, deletion is an event — or mutable when not derivable, where in-place updates and explicit transactional deletes stay legitimate. Everything the two architectures agree on ships unconditionally as the shared core: identity versus event tables, no nullable columns, no derivable columns, the state-derivation patterns, the lock discipline and commit-order rule for absolute-set events, the performance ladder. The stance decides only which write-discipline clauses weave in on top. Converging a project from one stance to the other is a project of its own; the option is what lets both architectures be first-class until such a project happens.

Where the stack layer ships a framework primitive, the primitive’s contract is part of the layer and is not optional. The action-input primitive is the proving case: two projects carried different implementations under the same name, differing in what wins when a route parameter and a form field share a name. The package ships one contract — a submitted form field wins for exactly the fields the form actually submitted, and route parameters win for everything it did not, so a schema’s coerced default can never silently overwrite a real parameter — and that contract is pinned by a test that travels with the primitive. The losing implementation’s companion doctrine (a rule forbidding parameter-named fields in form schemas, which existed only to dodge the clobbering) dies with it: converging on the sounder contract deletes a rule instead of adding one.

Machine surfaces (an MCP server, a public API) are governed by stack-neutral doctrine, enforced per stack. The core rule — every tool wraps a business function through the same layer the product uses, so the surfaces cannot drift apart — admits exceptions only by criterion, never by a hard-coded allowlist: a tool may stand outside the rule exactly when it is a pure context projection (reflecting the authenticated context back, with no business function to wrap) or an MCP-only transport primitive (the equivalent capability rides a different transport outside the tool surface, so a wrapped function cannot exist). Every excepted tool is listed in a committed, project-owned exception register with a one-line rationale, and the parity check reads the register, so an unregistered exception fails the gate — the same three-way split as every enforced rule: doctrine generated, checker per stack (package-generated where the package ships the stack, project content otherwise), register committed. The standard a machine surface is held to is capability parity with the product, written down in a committed parity standard; where a project declares a machine surface, the generated review skills audit changes to it against that standard by outcome fitness, never by endpoint existence — a surface can have every endpoint and still fail the person using it.

Two smaller convergences set precedents worth naming. When two projects’ skills disagree about a fact — what a shared library actually does — the source decides: the merged skill states the verified behavior, and the text that guessed wrong is simply corrected, because a skill that misstates a fact teaches the error to every future session. And on database identifier length, the rule is names in the source always equal names in the database: every declared identifier fits the engine’s limit, enforced by a deterministic check that fails the gate on any identifier the engine would silently truncate. Letting long names truncate was considered and rejected — it parks a divergence between source and database behind preconditions someone must keep true forever, and the first future by-name reference (a reindex, a drop, a query plan, a conflict clause) trips over it. Descriptive names still win; the limit is a naming exercise, not information loss.

The stack layer’s roster is bounded by the same rule that bounds the layers themselves: a skill enters the package at its second consumer, never its first. The skills exactly one project grew — an outbound-integration telemetry standard, spreadsheet import/export doors, a host-specific deploy pipeline, a billing registry, an internal architecture map, an in-app user manual, a mobile-shell verification counterpart — all stay project-owned committed skills, untouched by generation, which the shared-folder model already accommodates. However portable one of them looks, its portability is a hypothesis until a second project actually adopts it; that adoption is the event that moves it into the package, and packaging ahead of it would be the premature convergence the drift-versus-legitimate-difference lens exists to prevent.

The package also teaches agents to run it. It ships a skill about itself: how to install, how to configure, how to upgrade. New versions arrive with migration instructions written for agents, so when an upgrade brings breaking changes or new configuration, an agent performs the upgrade the way it performs any other work — upgrading the workflow is itself agent work.

The books and posts our shaping practice leans on are never inside the package. The package carries machinery instead: it fetches the freely published sources from their authors’ own sites at install time, and for the one commercial book it asks for the user’s own copy — when none is provided, the skill is generated with our own distilled account of that book’s method, written in our own words.

And this repository is the first consumer: the workflow’s own home installs the package, configures it, and works under the very rules it ships. The project’s final stage then migrates our three active projects onto the package — the install replacing everything each of them grew by hand. That migration is the framing’s outcome test run for real: three different stacks, three different configurations, no capability lost — and it doubles as the quality assurance pass, because any gap between what the package generates and what a project relied on surfaces there, before anyone else adopts it.

Walkthrough

Replay the framing's story — the same person, the same moment — with this in place. Step by step, in their words, so the reader can check it against how the work really goes.

  1. An agent in one project trips over something — say, that one-line shell mistake — and the lesson is learned. Instead of editing that project’s own instructions, the lesson is written once, into the package’s source.

  2. A new version of the package is released.

  3. In each project, an agent performs the upgrade: it reads the version’s notes, adjusts the configuration if the notes ask for it, and regenerates every instruction file. The lesson now exists everywhere.

  4. The next session in any project carries the warning. The mistake that once cost an afternoon in a sibling project cannot repeat anywhere — the warning travels by default, not by memory.

  5. And when a new project joins: install, configure, generate. The full way of working arrives in minutes, current to the latest version, with nothing copied by hand and nothing to prune.

Time bombs

The places where this could blow up mid-build. Each one is defused here, in this document, before the build starts.

The package is public, but the shaping practice leans on books and talks that belong to their authors.
How we defuse it The package distributes machinery, never texts. Freely published sources are fetched from their authors’ own sites on the user’s machine; the one commercial book is built only from the user’s own copy, with our own distilled account as the fallback; every built corpus is gitignored; and the repository’s history was recreated clean, with open-sourcing set to publish from a fresh repository.
Configuration sprawl quietly reintroduces the drift this project exists to kill — every option doubles the space of generated output nobody has read.
How we defuse it An option exists only where a genuine, durable difference between projects demands one. Our active projects’ configurations are the tested combinations, and an option no project uses gets deleted.
A breaking upgrade strands a project on an old version because nobody wants to do the migration by hand.
How we defuse it Upgrades are agent work. The package ships a skill about itself, and every version with breaking changes or new configuration arrives with migration instructions written for an agent to execute.
Someone hand-edits a generated file, and the edit silently dies on the next regeneration — or worse, survives as a local fork.
How we defuse it Generated output is gitignored and rebuilt at will, so a hand-edit cannot be committed and cannot survive; the only two doors for change are the project’s configuration and the package’s source.
The unified instructions bloat: merging every project’s hard-won rules produces doctrine that taxes every session’s attention forever.
How we defuse it Where variants differ, the leaner one wins unless the longer one demonstrably changes behavior — and a rule that exists only to compensate for a degraded orchestrator is bloat, not refinement, and is dropped.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • No adoption smaller than a layer. A project cannot pick individual pieces à la carte; a layer comes whole or not at all, because its pieces reference each other.
  • Not a marketplace. The package ships the Seasoned workflow and nothing else — it is not a general registry for third-party skills.
  • No copyrighted text ever ships in the package or enters the repository, even while it is private.
  • The growth-frameworks material and the talk and interview transcripts are out of the workflow entirely.
  • Deterministic size-testing of instructions — machinery that measures and bounds how much context the workflow itself consumes — is a future project, not this one. Here we only hold the line by judgment.
