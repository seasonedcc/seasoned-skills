Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

One person runs several products, and over the last years built a single way of working across all of them: standing instructions, step-by-step guides for recurring work, and small tools, all aimed at one goal — AI agents doing all the work, from pulling requirements out of meetings and out of the running product’s behavior, through framing and shaping, to building, releasing, and watching what ships. Not every step is fully theirs yet, but no person builds anything by hand anymore. Each project keeps its own hand-made copy of that way of working. On the day this project was framed, an agent working in one repository made a one-line mistake that another project’s instructions had explicitly warned against for weeks — the warning simply never traveled. That is the pattern: every lesson is learned once but taught to only one project, and the person who maintains all the copies is the only bridge between them.

Today’s way, and where it breaks

The way of working spreads by hand: when a piece of it improves in one project, someone must remember it exists elsewhere, copy it over, and adapt it — once per sibling project, for every improvement. In practice that rarely happens, so the copies drift. Measured on the day of framing, over the nine guides that existed in all three projects’ folders that day: exactly one was still identical everywhere — every other copy had quietly forked. Starting a new project means copying from whichever existing project feels most current and pruning what does not apply, with no way to tell later which parts are behind.

The outcome test

Take any of our active projects, remove every hand-maintained piece of the way of working, and install this package in its place: the project works as it did before — no capability lost, and everything that was particular to that project preserved through its own configuration. From that day on, staying current means upgrading a version, and a lesson written once reaches every project on its next upgrade.

Why now

Agents now do the work end to end, so the way of working — not any single product’s code — has become the company’s biggest compounding asset, and it is the one asset currently maintained by hand in parallel copies. Every week of three-way drift makes the eventual reunification harder, and the next project to adopt the workflow should cost an install, not an afternoon of copying and pruning.

The big hire and the little hires

The big hire is deliberate and total: a project adopts by handing its whole way of working to the package — all or nothing. The install takes over the project’s standing instructions, its guides, and its supporting tools from day one; there is no half-adopted piece — the install takes over the whole of what it covers — and that is a promise, not a limitation.

The little hires are the upgrades: each new version quietly bringing every project the newest lessons, and each newly-learned lesson written once, in one place, with certainty it will reach everywhere.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

The whole way of working — the standing instructions, every guide, the small supporting tools — moves into one published package that any project can install: seasoned-skills, on npm, this repository’s namesake. A project adopts it by installing the package and filling in one configuration file; from then on, staying current means upgrading a version.

The heart of the idea: nothing the package produces is ever written by hand inside a project again. From the configuration plus the package’s own content, the install generates every instruction file the project’s agents read. The line between generated and owned is sharp: nothing generated is ever saved into the project’s history, and what a project keeps is what is genuinely its own — the configuration file and its own content, kept wherever it prefers. Everything generated is disposable and rebuilt at will.

▸ Contract What the install materializes, and what a project commits

Generated and gitignored: the project’s agent instructions file, every skill the package ships, the hooks, and the supporting scripts. Committed by the project: seasoned-skills.config.ts at the repo root, plus the project-owned content it points at — one content directory, one file per generated skill and one for the doctrine layer, carrying project facts, custom instructions, design-system vocabulary. Published: a public npm package under an MIT license — the package carries only our own prose and machinery, plus one openly licensed font that travels with its own license file.

The package shares the agent-configuration folder with the project; it never owns it. A project keeps its own committed skills alongside the generated ones — skills it wrote and skills it vendors from third parties, pinned by its own lock machinery — and its own additions to the agent settings. The tool’s managed footprint is two files and one script entry. In the ignore file, a script verifies that every path the package generates is effectively ignored — by asking git itself, never by grepping for a pattern, because a repository may ignore by whitelist and a present-looking entry can still not take effect — and adds only the entries needed to make it so, never removing or reordering anything the project put there; in the settings file, the tool enforces the values of the keys the workflow depends on and leaves every other key untouched. Check-and-edit, idempotent, in both files — and the same discipline keeps the one managed script entry, the sync wiring, in place.

Installing assumes a codebase that is ready for the workflow, and the package’s README says so before it says anything about installing. The workflow’s criteria lean on machinery the package does not create: a route surface the stack can enumerate and an end-to-end suite that can reach it, the seed pipeline the demo-seed criterion asserts, gates a continuous-integration run can execute, a repository worktrees can be cut from, and the package itself pinned at an exact version — the premise pre-1.0 upgrades rely on. The README walks an adopting user through the prerequisites — for each criterion and layer, what it assumes of the codebase and what to put in place before installing. The configuration keeps the switched criteria off until their machinery exists; the unswitched ones arrive with brownfield on-ramps rather than off switches — the coverage register seeded shrink-only, the excused-surfaces list carried over. The same section covers the machine: the binaries and services the enabled workflow needs, the same list the doctor subcommand checks mechanically.

The shaping practice’s scaffolding follows the same rules as everything else, with no special files. The install creates the shaping folder, and the document assets — the stylesheet, the document script, the drawing library that committed documents load by relative path — are generated and gitignored like every other generated file: reading a document from a fresh clone means installing first, the same requirement the rest of the workflow already carries. Because committed documents outlive package versions, the assets are a compatibility surface: an upgrade must keep every previously committed document rendering correctly — the class vocabulary and drawing interface evolve append-only, and the package’s golden-output tier renders an old fixture document — and an old fixture meeting page — against the new assets to pin it. Standing project principles — the rulings that bind every session in a repository — are regular injection, not a hardcoded file with a hardcoded name: the shaping skill reads them from its own project-content section, and the meeting-requests skill does the same with its house doctrine. The registry of documents is the folder itself, derived by scanning — nothing to maintain, nothing to drift.

The meeting-requests practice splits the same way. Its data folder — the meeting records, the source assets and their manifest, the stakeholders file — is committed project content, scaffolded by the install and owned by the project forever. The machinery that today lives inside that folder moves out: the verbatim-quote verifier is generated into the gitignored tree like every other script, and the stylesheet the committed meeting pages load follows the document-assets rule — generated, gitignored, evolving append-only under the same keep-old-pages-rendering contract. The manifest’s schema is package-owned surface, versioned with the verifier that reads it; the manifest’s contents are project data. Where the recordings live is a fact about a machine, never about the project, so it has no committed configuration at all — only a personal, gitignored config.local.json beside the data folder, the same species as personal settings, which the skill documents and asks for when missing. The transcription toolchain the practice depends on is pinned by the package and checked by doctor, so a transcript comes out the same on every machine.

The demo-video practice ships its machinery the same way. The rendering rig and the narration engine are package deterministic code, generated into the gitignored tree, and their tests move into the package alongside provisioning’s. Each video’s screenplay folder is committed project content; rendered output never is. The model weights the narrator runs on are never in the npm package, and the adoption install never fetches them either: a once-per-machine setup step of its own fetches them — about three gigabytes — into a local, gitignored cache, with the narration voice pinned by checksum so every machine speaks with the same voice, and the toolchain, pinned like the transcription one, declared to doctor. The practice consumes the seed pipeline the demo-seed criterion asserts: demo state is seeded, never hand-crafted, so any video can be re-rendered from scratch.

▸ Contract The package’s own stack

The package is TypeScript on Node, published to npm with the command-line tool as its binary. The configuration file is real TypeScript: the package exports its types, so a project’s editor flags a bad option before the tool ever runs, and the tool loads seasoned-skills.config.ts through an embedded TypeScript loader, so consuming projects need no build step of their own. Prose stays markdown; weaving is code: skill and doctrine text lives as markdown fragments — diffable, editable prose — and typed composition functions assemble each generated file from those fragments according to the configuration. There is no text-template language, because layer and option weaving is conditional logic, and it deserves type-checking and unit tests rather than template conditionals.

Two test tiers, both in the package. Unit tests cover the deterministic code — provisioning, the footprint managers, the sweeps. Golden-output generation tests cover the weaving: synthetic fixture configurations mirror the tested combinations — one per active project’s shape, carrying no project identity, plus this repository’s own, the project shapes drafted from the references library’s variants and trued up against the real configurations when the migration stage begins — with the full generated tree snapshotted, and every tested value of every option covered by at least one fixture. This makes the option-discipline rule executable rather than aspirational, and it means a template change is reviewed as a diff of what projects will actually receive, not a diff of template internals. Releases are semantic versions on npm, each shipping its agent-readable migration notes; the repository runs the release practice the package ships, and its own stack layer stays off — the package is a command-line tool, not a web application. Versioning starts at 0.0.1 and stays below 1.0 deliberately: pre-1.0 releases promise no stability, so breaking changes land in any release without the ceremony of a major version — safe for consumers because every project pins an exact version and every upgrade is an agent-executed act that reads the migration notes and regenerates the world. Reaching 1.0 is a milestone the package earns, not a formality.

Consumer zero holds itself to the adopter’s bar. Before the workflow is installed into this repository, the repository puts in place everything its own README demands of an adopting codebase, in the form that applies to a command-line package with its stack layer off: a continuous-integration pipeline of its own whose jobs run both test tiers and stand as the required checks the default branch’s protection enforces, test coverage comprehensive enough that the workflow’s gates gate something real, and the machine prerequisites the doctor subcommand checks. Building that machinery is part of this project, not an assumption — a package whose own home failed its README’s checklist would be shipping advice it does not follow.

Because instructions are generated, differences between projects stop being forks and become configuration. Divergence comes in two kinds: drift — the same rule aging differently in each copy — which generation eliminates; and legitimate difference — a team repository versus a solo one, a stack without a given technology, a practice one project is not ready for — which the configuration expresses. Giving legitimate difference a home leaves illegitimate difference nowhere to hide.

The workflow is organized in layers. One of them is optional today — and the machinery stays ready for layers to come. Enabling a layer composes it into everything else: every generated instruction that should mention it starts mentioning it, and disabling it removes every trace, so no instruction ever points at a practice the project does not run. One discipline keeps this honest: a configuration option exists only where a genuine, durable difference between projects demands one — our own active projects’ configurations are the tested combinations, and an option no project uses gets deleted.

Concretely, the package has five layers. The doctrine layer is the standing instruction file every working session reads first. The practice skills are the guides for how work is done — orchestrating agents, testing, reviewing, shaping, releasing — and every one of them comes with the workflow, whole, because every project we run uses all of them. The stack layer — the guides tied to one specific technology stack — is the only optional one: a project declares its stack, or doesn’t. The deterministic code layer is the small supporting tools: the scripts, the hooks — small guard scripts the agent’s tooling runs automatically at set moments — and each project’s runtime settings. And the corpus machinery builds, on each person’s own machine, the reference library the shaping practice reads from. The configuration decides which layers materialize — and a new skill enters the package only when a second project needs it, never on the hope that one someday might. The rule gates entry, not authorship: a practice every project already runs comes in even where only one project had written it down.

▸ Contract Rulings — how work flows

From the doctrine adjudication: agent merges to the base branch during a goal are off by default and opt-in per project; everything else unified with no option — checkouts never leave the default branch (documentation work uses an unprovisioned worktree), questionnaires only when the user may be away, browser verification for any work that could affect user-facing behavior, the reference-privacy rule everywhere and not toggleable (names allowed in conversation and subagent charters only, never in anything repository-visible), the leaner one-question rule (what that ruling drops is exactly one thing, the multi-select batching elaboration one variant grew as a patch for degraded orchestrator behavior; the question-discipline sentences around it do not conflict and merge in), the responsive bar’s stack-neutral core with framework-coupled lines injected from project content, and the quality bar’s design-system clause restored. Backwards compatibility is a confidence judgment, never a blanket ban: the generated rule reads “do not add backwards compatibility unless you are 100% confident it is necessary”, and a project’s real compatibility contracts — a GA API surface’s consumers, live integrations, frozen legacy surfaces — are named from its own content, so the same rule serves greenfield and long-lived projects alike.

From the skills adjudication: what an agent does with breakage it discovers outside its task’s scope is the second option. In every project, every finding gets an explicit disposition the moment it is confirmed — nothing parked undecided, nothing dropped. But only projects that opt in let agents fix discovered breakage autonomously, under a codified Definition of Broken — a failing gate, a reproducible runtime failure, a violation of written doctrine; never a judgment call. Projects not ready for that level of autonomy get the conservative default: out-of-scope findings are banked with evidence and adjudicated with the user. In both modes, an out-of-scope fix executes in its own dedicated pass, never inline in the lane that found it — that is what keeps lanes convergent and review rounds terminating.

Also from the skills adjudication, no option: a pull request opens as a draft the moment the fast gates pass — so continuous integration overlaps with local verification — and flips to ready for review only after the full pre-merge pipeline completes: builder claims verified, full gates green, the adversarial review done, and a ruling on every confirmed finding. The adversarial review is the package’s own pull-request-review loop, run against the draft pull request — the review family ships with the core, so every project runs the same loop, and it supersedes the code-review loop in the Definition of Done everywhere: no project’s pipeline ran this way before the package, so the switch is a migration behavior change for all of them. Reviewing the draft is deliberate: the loop reads the pull request’s description and discussion alongside the diff, which a bare diff review never sees. The loop’s angles include a conventions-compliance pass — the change judged against the project’s own committed conventions and doctrine — absorbing what one project ran as a separate step. Small diffs are not exempt from the pipeline; they simply overlap it. Paid auto-reviewers are the consuming repository’s concern: configure them to ignore drafts.

Long gates belong to the orchestrator, no option: a builder’s charter ends at commit — or commit and push — and stops there, with only the fast, cheap checks (lint, type-checking the affected files) run in the builder’s own foreground. The orchestrator runs the full gates itself as its own background shells, owns pull request and merge outright, and owns push whenever the charter stopped at commit. This is a structural fix, not an exhortation: instructing builders to run a long suite in the foreground does not survive contact with builders, who background the command and end their turn stalled.

The third option: how a branch reaches the mainline, and with it how a pushed branch syncs with its base — one setting, because the sync strategy follows from the merge strategy. A repository that merges pull requests with a merge commit keeps its branch history linear by syncing lanes with rebase, and carries the discipline that makes rewriting pushed history safe: patch-identity verification and post-rebase reconciliation. A repository that squash-merges syncs every pushed branch by merging the base in and never rewrites pushed commits — the branch’s intermediate history vanishes at the squash, so merge commits cost nothing. Each mode weaves in only its own pushed-branch discipline — but rebasing a branch nothing else references yet is legitimate in both modes, so that discipline, with its pre-rebase conflict-surface check, weaves in everywhere; what the modes never mix is how a pushed branch syncs and lands.

Long-lived processes, no option: every process a lane needs beyond a single turn — a development server, a worker — runs as its own harness background task, never forked with & inside another task’s shell, and every lane process is swept at session end. The double-fork detachment helper one project grew for this is judged a workaround for an older harness and is retired, not shipped; the migration verifies current harness behavior as its closing check.

A continuous-integration watch is a completion signal only, no option: its exit code is never the verdict — the watch command has reported success on genuinely failed runs — and the verdict comes from a fresh direct read of the check states after the watch returns, before anything acts on it.

The Definition of Done itself is generated from one composition, the same way a skill is. The package contributes the core criteria — gates green, no leftover comments, the review loop run against the branch’s committed diff, browser verification, the responsive bar, the coverage register, the closing self-improvement pass — each carrying the project’s facts as parameters: its gate commands, its register paths. A core criterion weaves in only where its subject exists: browser verification and the responsive bar bind a project whose configuration declares a user-facing web surface, the coverage register binds where there are routes to cover — so a command-line project’s composition, consumer zero included, simply has no line for them. Two more criteria are first-class core citizens switched by their own configuration: the demo-seed criterion — every new or changed user-facing surface ships its seed section and its entry in the committed seed manifest in the same change, or is declared unseedable there with a written reason, with the seed single-shot and fail-loud behind an empty-database preflight — and the machine-surface parity criterion, on whenever the configuration declares a machine surface. The demo-seed criterion converges on the strongest form any project reached: the denominator of surfaces is derived from the stack’s own route enumeration, never maintained by hand, so a surface nobody covered fails the gate outright instead of depending on review-time honesty. The deriving checker is stack-layer code — and for the packaged stack it is new code, not a port: the strongest form was reached on a stack the package does not ship, and the packaged stack’s existing route enumeration is the raw material, not the finished checker. A stack that cannot enumerate its surfaces carries the review-time caveat in its criterion text instead — honestly, as the weaker gate it is. Beyond the core, a project injects whole criteria of its own from its content — each phrased as “a task is not done if…” and each backed by the project’s own gate or committed skill, per the enforcement split. The documentation-only carve-out is part of the core: when every file in the diff is prose the application never loads, the checklist collapses to the handful of criteria that can still apply — which release-triggered files get no such pass is a project fact.

And because the list is composed, its reduced form is derived, never forked: every criterion — core or injected — declares its quick-mode disposition (kept, reduced, or excluded by the qualification criteria), and the quick skill’s reduced Definition of Done is generated from the same composition as the full one, so the two can never drift apart. The qualification disqualifiers compose the same way: the package’s base list — a new route, table, permission, or product surface — plus whatever the project adds from its content. Injecting or changing a criterion includes declaring its quick disposition in the same change, the calibration discipline again. Quick mode itself stays explicit-only everywhere: only the user’s command turns it on, never the agent’s own judgment, and never a suggestion.

▸ Contract Rulings — testing discipline

The full end-to-end suite is continuous integration’s job, never a local step, no option: locally a lane runs the specs judged related to the change — related by the change’s blast radius, not literally the specs of the files touched — and the full-suite verdict comes from the integration run on the draft pull request, read fresh.

The coverage register, no option — one rule with a brownfield on-ramp: a new surface and the spec that reaches it land in the same change, and the coverage register — the shrink-only list of unreached surfaces — stays empty. When the coverage gate is installed into a project that already has unreached surfaces, the install seeds the register with them; it only ever shrinks, and once empty it is held empty forever. A surface that genuinely cannot be reached by a spec is excused instead, on a separate committed list that admits an entry only with a one-line written rationale — and “no spec yet” is never a rationale.

Specs never assert one-shot flash messages, no option: their delivery rests on a global no-prefetch property any future change can silently break, failing every such assertion at once. Specs assert the destination and the re-navigated state instead.

No cap on concurrent suites, no option: the orchestrator owns every long gate run, so it schedules heavy suites by judgment when lanes pile up, and a contention-shaped failure — connection exhaustion, timeouts under load — is re-run alone before anyone treats it as a defect. A machine’s real capacity limits are that project’s own facts, not package doctrine.

▸ Contract Rulings — skills in practice

The design-system guide is generated in two parts: the package’s standard guidelines — the design doctrine every project shares, such as token discipline, the typography tiers, the closed status vocabulary, the responsive canon, and the shape of a confirm — woven together with the project’s own design-system guidelines from its content files: its palette, its component library, and its concrete idioms. How a specific idiom renders — how a status presents on a phone, for instance — is adjudicated inside the project’s own guidelines, within the standard doctrine’s bounds.

Browser hygiene splits by audience, no option: the lane-side discipline — one session for the whole run, named after the lane, closed before reporting — lives in the browser skill, and the orchestrator-side discipline — a reported close is not evidence the processes died, sweep to zero between waves, a gate that turns flaky while browser work is in flight is a leak suspect before it is a product bug — lives in the orchestration skill, because the orchestrator rarely loads the browser skill. The never-pattern-kill rule is embodied, not repeated: the package ships two sweep tools — a browser sweep, and a lane-process orphan sweep that lists and kills processes by lane, wired to run at session end and runnable by hand — and both kill only by exact process id, so every kill passes through a tool that enforces the rule. Lane teardown also kills whatever listens on the lane’s ports, so a worker stack orphaned by a killed run cannot outlive its lane.

Saved browser state — cookies, sessions — always goes to an absolute path in the scratchpad directory, never a relative one, no option: relative paths have landed credential files inside repository checkouts. Every example in the generated skill complies, and stale counter-examples die at generation time because the whole skill is regenerated from the package.

The skill roster ships in two tiers: the core — every practice skill, from orchestration and subagents through shaping, meeting requests, releases, and demo videos — comes with the workflow whole, because every project we run practices all of it — today each repository carries only the guides it wrote itself, and the install brings the rest; only the stack-coupled skills form a separate layer, keyed by the stack the configuration declares. The layer machinery itself stays composable for the layers still to come — performance optimization, observability — and a practice skill splits out into its own optional layer only when a real consuming project actually runs the workflow without it. One skill dies rather than ships: the standalone idea-grilling skill is absorbed by the shaping practice, which interrogates ideas as a matter of course.

Self-improvement runs on two channels at once, no option. When a lesson is learned, the agent solves the problem locally — a pull request on the project, landing the lesson in the affected skill’s content file or the project’s own committed material — and, in almost every case, also files a detailed issue on the package’s repository, never a pull request there: the full scenario that suggested the improvement, the situation’s details anonymized to the same standard as everything else repository-visible, and suggested changes marked as exactly that — suggestions. Both by default, because a workflow that asks the agent to choose between the two channels breeds a bias toward one; the only exception is the lesson so obviously project-specific that it will never benefit another project, which stays a local pull request alone. The package side keeps its own discipline: a demand on the shared workflow needs shaping, not application, and applying every consumer’s request verbatim would braid the projects’ reflexes into doctrine nobody ruled on. The package changes only through its own process, with the issues as its demand records. And because a workflow change is doctrine about how a team works, a self-improvement pull request is marked ready only by the user, on every repository — no change to the way of working reaches teammates before the user has read it, and the rule carries no team-or-solo judgment for an agent to make: on a solo repository it costs nothing, since only the user could flip it anyway.

Subagent calibrations follow the design-system precedent, no option — but with a discipline of their own, because calibrations are not static project facts: they are living judgments about how big a slice of work is, which model tier it needs, and when to split, and every one of them is implicitly relative to the project’s Definition of Done. The generated subagents skill weaves the package’s generic doctrine — sizing is design work, the stopping protocol, slicing — with a committed, project-owned calibration file the configuration points at. The package ships the discipline, never the numbers: calibrations are stated relative to the Definition of Done, and any change that expands the Definition of Done carries a calibration review in that same change — a gate added without re-deriving what a unit of work now costs is an incomplete change, because every calibration just silently went stale. When the expanding change is a package release — a new core criterion arriving from upstream — the release’s migration notes carry the calibration-review instruction, and the agent executing the upgrade discharges it in the project, so the discipline survives the one expansion path that happens in a different repository. Calibration updates are lessons about the project itself, so they travel as pull requests on the project; installing into an existing project seeds the calibration file from whatever calibration text the project already carries.

That precedent generalizes into a uniform contract: every generated practice skill has a project-content slot, and the doctrine layer has one of its own — the file whose project facts the generated instructions weave in. The configuration names a content directory with one file per skill, and generation weaves that file into the skill as a project-specifics section at a defined anchor — empirical observations, local protocols, whatever the project has learned that is true of itself and not of the workflow. The woven section may also carry a conditional protocol that supersedes the generic flow for a declared class of work — where the project’s section says “for this case, the rules above change”, the project’s word wins. The structured slots already ruled — the design-system guidelines, the calibration file, the stack-off testing stub — are specializations of this contract, not exceptions to it. The weave reaches the skill’s front matter too: the one-line description that decides when a skill activates carries the project’s own trigger vocabulary alongside the package’s, because a description written only in the package’s words silently de-activates the skill for the phrases the project actually uses. Each generated skill states where its lessons go: a project-empirical lesson about a generated skill lands in that skill’s content file through a pull request on the project — the skill never instructs an agent to edit the skill itself, because the generated text is rebuilt on every upgrade. And when a fragment of project content turns out to be true of every project, that is a package demand like any other: it travels as an issue, gets shaped, and moves into the package’s generic text, leaving the content file thinner. The boundary between the two is discipline versus fact: method that holds anywhere — how to diagnose, what to measure, what a trend means — generalizes into the package’s text, while the measurements themselves, the named surfaces, and the known residual hazards — the things only this project could know — stay in the content file, and the generic text is written so the project section slots in naturally beside it. Machine-local values — a personal recordings path — live in the personal gitignored local file the relevant skill documents; machine-bound prose, by contrast, gets no structure of its own — deliberately: the cases found in the wild dissolve into conditional discipline in the package’s text (“when the host behaves like this, do that”), applied by observing the host at hand, and a parallel tree of per-machine content files would buy that one case at the price of complexity and drift. If a genuinely machine-bound instruction ever needs a durable home, that is a package demand like any other — an issue, shaped when it is real.

The references library says these notes name each merged skill’s base, so here is the merge table, settled during the layer walks. The variant letters are the references library’s own; the same source system is the same letter everywhere. A base decides where merging starts, never what was ruled: everything one variant carries and the others simply lack merges in mechanically; where variants disagree with each other about the same rule, the leaner text wins unless the longer one demonstrably changes behavior; the grafts named below are the load-bearing ones; and wherever a variant disagrees with a ruling in these notes, the ruling wins. One core skill appears in no table because it has nothing to merge: the shaping skill’s single source is this repository’s own committed copy, and its corpus fetch list is the one that skill’s own reference index already names. For the doctrine file, variant C is the base — the most evolved of the three — taking the union of every non-conflicting rule from A and B: notably A’s Definition-of-Done frame with its documentation-only carve-out, the review-the-committed-branch-diff criterion with its wrong-directory trap, the parallel-family browser rule, the end-to-end-filter footgun, and the shell word-splitting rule; and B’s check-integrity baseline, ledger-currency clause, never-pattern-kill rule, and extra responsive-bar items — with the design-system quality-bar clause variant C had dropped restored. For the practice skills:

  • orchestration — base C (it alone carries the browser-hygiene section, the raw-spec cache, the allocation table, the never-block-on-a-running-subagent rule, and the strongest pull-request-body doctrine), with variant B’s judgment rules merged in wholesale and variant A’s two surviving orphans kept: one mutating agent per worktree, and the agent-id lookup.
  • subagents — base B (the watchdog, the stopping protocol, the richest dynamic-workflows section, sizing-is-design-work, and the calibration frame), plus the two workflow rules variant C alone carries — dedupe findings before spawning verifiers, and the spawn working-directory artifact — C’s sharper phrasings of the isolation and backtick traps, and variant A’s design-tier paragraph.
  • testing — no single base: variant A supplies the diagnosis half (CI-versus-local divergence, racy-by-design suites, scratch-database pipelines), variant B the harness-architecture and assertion-hazard half (worker isolation, pools, teardown leaks), and variant C’s pointer shape — a thin skill naming the project’s own committed playbook — is the package’s pattern for projects whose stack the package does not ship.
  • worktrees — base C’s lifecycle structure (the user-driven-lane protocol, the read-only-lane rule, the pre-teardown live-reader check, the explicit base), injecting variant A’s process, kill, and cache guardrails and variant B’s teardown operations and base-move staleness rules.
  • design-system — base B, the only variant carrying the responsive canon, print, and flow design together, plus variant A’s motion and navigation-shell material; only the generic core ships, per the ruling above.
  • agent-browser — base B, decisively (its failure-mode list is the longest and it alone carries the leak-and-teardown doctrine), plus variant A’s absolute-state-path and debounced-fill rules and variant C’s implicit-form-submission failure mode, with the synthetic-event and clearing rules phrased stack-neutrally the way variant C phrases them.
  • self-improvement — a mechanical union of all three; no adjudication was needed.
  • the review family and main-branch sync — variant C’s files, the only copies; quick — variant A’s, its hand-maintained criteria list retired in favor of the derived composition; release, meeting requests, and demo videos — variant B’s, the only copies.
  • skill management — the one guide still identical everywhere, taken as is — and the roster’s one rename: skill names name the practice, never a role, so the file the projects carry under a role name ships as skill-management. No other skill renames.
▸ Contract Rulings — runtime and deterministic code

The runtime assumptions the workflow depends on — the model and its effort level, always-on thinking, automatic compaction and memory off, the permission mode defaulting to auto, the status line with its model-demotion alarm — are materialized per project by the command-line tool as deterministic code. The settings file itself is committed and project-owned, managed surgically: the tool enforces the workflow’s keys — the runtime values above, the skill-listing budget, the shipped hooks’ wiring — and leaves every other key untouched, so a project’s own keys and its own hook registrations ride in the same file, and the workflow’s assumptions travel to every teammate through git. The permission default is the one permissions key the tool manages; everything else under permissions — allowlists, personal grants — stays in the personal, ignored local settings file where it lives today. The status-line script is generated and gitignored like every other generated file. Nothing ever writes to a user’s global configuration; personal permission lists and machine-local preferences stay personal. The workflow’s assumptions travel with the project, not with the machine — and what the machine itself must provide is declared, not assumed: the tool ships a doctor subcommand that derives its checklist from the configuration — every enabled layer, criterion, and skill declares the binaries and services it depends on, and project content declares its extras as project facts — then checks presence and versions and prints what is missing with install pointers. The install runs it, and it runs on demand, so a missing tool surfaces before the workflow trips over it mid-session. It is advisory everywhere — it never blocks an install or a sync; enforcement lives in the gates that need the tools, which fail loudly on their own. The status-line script itself — our own tool, previously maintained on its own — is absorbed into the package outright, so one upgrade updates it everywhere it is materialized.

Worktree provisioning, no option: one TypeScript implementation in the package replaces the three divergent copies, driven entirely by the resource table the project’s configuration declares — which databases, which port bases, which services, which repositories. The lifecycle contract is the part all three copies already agreed on: resources allocated by deterministic hash of the lane name and recorded in a managed environment block that doubles as the idempotency sentinel; setup safe to re-run; teardown that drops only namespaced resources and never touches the branch. The provisioning logic is unit-tested once, in the package — projects stop carrying their own copies of the scripts and of the tests that guard them. The unified code starts from variant A’s implementation, and both TypeScript copies come with test suites of comparable weight: A’s suite is the structural base, B’s cases merge in, and the unified suite meets the higher of the two bars — while the behavior absorbed is variant C’s multi-repository matrix and variant B’s port blocks.

That one implementation absorbs the richest behavior any project reached, configuration-driven, with no extension points: per-repository provision steps and seed commands declared in the resource table; seeding only the databases created in that same run, so a re-run never overwrites a lane’s data; skip flags for provisioning and for seeding; probing before starting shared services the machine may already run; a cache-store index allocated per lane and flushed at allocation, so no lane inherits another’s leftovers; and a teardown that refuses a dirty tree unless forced and drops the lane’s whole derived-database family — the derived-name patterns live in the same table, so nothing derived is ever orphaned. Template-database caching is a core capability keyed by configuration: the expensive migrate-and-seed result is kept as a template database whose fingerprint — content hashes of the migration and seed sources, plus the date the seed ran — is stored on the database itself, and a lane copies the template in about a second; a changed source or a stale seed date rebuilds the template transparently, and a flag forces the demo data to re-anchor to today. The worktrees skill gains the user-driven-lane discipline as generic doctrine: a lane handed to the user is the user’s — the delegated routine is fetch and fast-forward, stopping on divergence; sync dependencies; migrate; restart the server by the process id the lane records; verify it answers — and anything beyond that routine that would change database state asks first, because the lane’s data is the user’s working state.

Hooks, settled per hook. The package ships exactly three. The stash blocker: the stash stack is shared between the main checkout and every worktree, so one lane’s stash can silently destroy another’s uncommitted work — the rule lives as enforcement, with no prose twin. The session-end sweep, already named, killing orphaned lane processes by exact id. And a guard that blocks the harness’s own worktree-isolation option with guidance instead of letting it half-work: a harness-created worktree is unprovisioned, so an agent spawned into one believes it has a lane and runs against resources it does not own — the guard redirects to the provisioning command for a real lane, or a plain git worktree add for deliberately unprovisioned work like read-only review. The worktree create-and-remove hooks two projects carried are not shipped: every project’s real practice is script-only, and the create hook’s one code path — provisioning harness-created worktrees — was recorded failing every spawn in the project that exercised it, forcing a doctrine workaround the guard now replaces at the root. The fourth hook the references library carries — explicit-working-directory enforcement — is not shipped either: it stays a project-owned hook in the workspace whose shape demands it, and the generated doctrine’s working-directory rule is written without the enforcement pointer, so no project inherits a reference to a script it does not have. Wiring entries for shipped hooks are managed keys in the settings file, written to guard for the script’s absence so a fresh clone that has not yet run the install still works — and every managed key that points at a generated path carries the same absence guard, the status line included; a project wires hooks of its own in the same file, in the keys the manager never touches.

One more deterministic piece ships with the subagents skill: the transcript watchdog, a script materialized at the skill’s own generated path that sweeps a running workflow’s agent transcripts and alarms the moment one crosses the context threshold. It stays because nothing replaces it — the harness has no mid-flight warning for a subagent growing past the point where its judgment can be trusted, so the watchdog is what catches a runaway lane while stopping it still saves the work. Its threshold and sweep cadence are package-versioned constants: tuning them is a release, not an edit, and every project alarms at the same line. The skill’s model guidance stays version-agnostic — tiers are named by family alias, never by a dated model identifier, so the doctrine survives model releases untouched. One rule from that guidance is retired rather than packaged: the standing model-substitution rule all three variants carry was written for a one-time availability event that has since passed, and doctrine that memorializes an incident is legacy, not discipline — the retirement is a three-way deletion.

The tool’s footprint stops at those two managed files and that one managed entry, and its commands are its own: provisioning and the other deterministic operations run as subcommands of the package’s binary, referenced by the generated doctrine directly. Two of those commands split adoption from upkeep. The install runs once, interactively, at adoption: it writes the configuration scaffold and the sync wiring, creates and seeds the committed artifacts the workflow reads — the shaping folder, the meeting-requests data folder, the calibration file and the registers seeded from whatever the project already carries — builds the shaping corpus, asking for the one commercial book and falling back to our distilled account when none is given, and finishes by running sync and doctor. Sync is the non-interactive counterpart the prepare script runs forever after: it regenerates, never scaffolds, and never touches committed content — the corpus it weaves from is whatever the machine’s cache holds, rebuilt on demand by its own subcommand, with doctor reporting a cache that is missing or stale. The script manifest carries exactly one managed entry — the sync wiring: the project’s own prepare script runs the tool’s sync on every install, so a fresh clone materializes the whole workflow with the package-manager command the project already runs, and a version bump regenerates everything on the next install. It is the project’s own script deliberately: the package manager the projects pin blocks a dependency’s lifecycle scripts by default, and a sync that silently does not run is worse than none. A repository with no root package manifest at all gains a minimal one at adoption, so the same wiring carries sync there too. Sync is idempotent — regenerate every output, run the two managed-file scripts, re-assert the sync wiring itself, run doctor in warn mode. And sync fails loud: the content files the configuration names are mandatory, so an absent one — a new skill’s stub an upgrade never created — fails the sync rather than weaving an empty section. A failed sync leaves no half-generated workflow behind to run sessions on stale doctrine: it deletes every generated file except the package’s own skill, and generates in their place a minimal instructions file carrying the full error report and one standing order — tell the user the workflow cannot run, and propose the fixes the errors point at, with the surviving package skill as the repair kit. The failure surfaces at the right gate on its own: an upgrade lands as a pull request, that pull request’s continuous integration runs the package-manager install, the install runs sync, and the omission turns the pull request red before it can ever reach a teammate’s clone. Beyond that one entry, no script entries are managed or required — the scripts the projects carry for this today are deleted, not adopted. Continuous-integration workflows are project-owned machinery, never generated: a workflow file must be committed to run, so a generated one would be hand-edited the day its plumbing needed a tweak. The package states a CI contract instead — for each enabled criterion, the jobs a project’s pipeline must provide: the end-to-end job the workflow treats as the acceptance gate, the gate jobs, the seed-manifest job when demo-seed is on — in the readiness documentation and the generated doctrine’s project facts; the criteria bind outcomes, never files. Lint exclusions for the workflow’s folders are adoption plumbing the project commits itself, on the same footing as the rest of its gate configuration.

Enforcement gates split three ways, no option: the rule (every surface reachable by a spec, every capability mirrored, every surface demo-seeded) is generated doctrine; the checking code that enforces it is package-generated in the stack layer, since walking a route tree is stack-specific; and the lists the check reads — the excused-surfaces list, the shrink-only coverage register, the seed manifest, the machine-surface exception register — are committed, project-owned files the configuration points at, because they are facts about the project that must survive regeneration. A project on a stack the package does not ship keeps its own playbook and its own checker scripts as project content, and the generated instructions point at them exactly as they point at package-generated ones — a stack layer earns packaging when a second project shares the stack, and not before.

▸ Contract Rulings — the stack layer

The database mutability stance is the stack layer’s deepest option, with exactly two tested values: append-only, zero exceptions — insert is the only write the application ever performs, deletion is an event — or mutable when not derivable, where in-place updates and explicit transactional deletes stay legitimate. Everything that is not stance-specific ships unconditionally as the shared core: identity versus event tables, no nullable columns, no derivable columns, the state-derivation patterns, the lock discipline and commit-order rule for absolute-set events, the performance ladder. The stance decides only which write-discipline clauses weave in on top. Converging a project from one stance to the other is a project of its own; the option is what lets both architectures be first-class until such a project happens.

Where the stack layer ships a framework primitive, the primitive’s contract is part of the layer and is not optional. The action-input primitive is the proving case: two projects carried different implementations under the same name, differing in what wins when a route parameter and a form field share a name. The package ships one contract — a submitted form field wins for exactly the fields the form actually submitted, and route parameters win for everything it did not, so a schema’s coerced default can never silently overwrite a real parameter — and that contract is pinned by a test that travels with the primitive. The losing implementation’s companion doctrine (a rule forbidding parameter-named fields in form schemas, which existed only to dodge the clobbering) dies with it: converging on the sounder contract deletes a rule instead of adding one.

Machine surfaces (an MCP server, a public API) are governed by stack-neutral doctrine, enforced per stack. The core rule — every tool wraps a business function through the same layer the product uses, so the surfaces cannot drift apart — admits exceptions only by criterion, never by a hard-coded allowlist: a tool may stand outside the rule exactly when it is a pure context projection (reflecting the authenticated context back, with no business function to wrap) or an MCP-only transport primitive (the equivalent capability rides a different transport outside the tool surface, so a wrapped function cannot exist). Every excepted tool is listed in a committed, project-owned exception register with a one-line rationale, and the parity check reads the register, so an unregistered exception fails the gate — the same three-way split as every enforced rule: doctrine generated, checker per stack (package-generated where the package ships the stack, project content otherwise), register committed. The split binds the machinery the package ships; a checker a project owns outright, backing a criterion the project injected, organizes itself as the project sees fit, and answers to the split only if it is ever promoted into the package. The standard a machine surface is held to is capability parity with the product, written down in a committed parity standard — a project-owned document the configuration points at, scaffolded with the exception register by the install when a machine surface is declared; where a project declares one, the generated review skills audit changes to it against that standard by outcome fitness, never by endpoint existence — a surface can have every endpoint and still fail the person using it.

Two smaller convergences set precedents worth naming. When two projects’ skills disagree about a fact — what a shared library actually does — the source decides: the merged skill states the verified behavior, and the text that guessed wrong is simply corrected, because a skill that misstates a fact teaches the error to every future session. And on database identifier length, the rule is names in the source always equal names in the database: every declared identifier fits the engine’s limit, enforced by a deterministic check that fails the gate on any identifier the engine would silently truncate. Letting long names truncate was considered and rejected — it parks a divergence between source and database behind preconditions someone must keep true forever, and the first future by-name reference (a reindex, a drop, a query plan, a conflict clause) trips over it. Descriptive names still win; the limit is a naming exercise, not information loss.

The stack layer’s roster is bounded by the same rule that bounds the layers themselves: a skill enters the package at its second consumer, never its first. The skills a single project grew — among them an outbound-integration telemetry standard, spreadsheet import/export doors, a host-specific deploy pipeline, a billing registry, an internal architecture practice, an in-app user manual, a mobile-shell verification counterpart — all stay project-owned committed skills, untouched by generation, which the shared-folder model already accommodates. (Two projects keep architecture skills of their own, but they are not the same skill twice — one is a practice for maintaining an architecture document, the other is the system map itself — so neither is the other’s second consumer.) However portable one of them looks, its portability is a hypothesis until a second project actually adopts it; that adoption is the event that moves it into the package, and packaging ahead of it would be the premature convergence the drift-versus-legitimate-difference lens exists to prevent.

The merge bases for the stack layer’s own skills, from the same walks and under the same rule — the base decides where merging starts, one-side-ahead material merges mechanically, and the rulings above win over any variant’s text:

  • authorization — B, with A’s resource-routes section grafted in verbatim.
  • background-jobs — A’s structure, plus B’s third-party-schema paragraph; the idempotency example becomes injected project content, the rule stated schema-agnostically.
  • business-folder — B verbatim; A’s domain-standard paragraph becomes injected project content.
  • composable-functions — A, the superset (it alone keeps the array-fields section), with B’s input-error wording; the action-input paragraph resolves to the contract ruled above.
  • database-design — B’s structure carries the shared core; the mutability stance weaves per the option above.
  • env-vars and nested-routes — B verbatim.
  • formatting-datetimes — B, with the time-zone model — tenant-configurable or a constant — as the injected project fact, because B’s shape degrades gracefully to a single zone and the reverse does not generalize.
  • framework-folder — already identical across variants; its one variable, the application root, is injected.
  • kysely — B, its insert-only section conditional on the mutability stance, the identifier rule per the invariant above.
  • mcp-server — B, adding A’s role-scoped context-augmentation pattern as a named shape and A’s date-only schema variant.
  • optimistic-ui — a true union: B’s three doctrine sections and fetcher criterion, with A’s two worked patterns restored, because neither file alone is adequate.
  • type-safety — the two variants are substantively identical; A’s text, unpinned from any library version, with the project’s key-types list as the injection slot.

The package also teaches agents to run it. It ships a skill about itself: how to install, how to configure, how to upgrade. New versions arrive with migration instructions written for agents, so when an upgrade brings breaking changes or new configuration, an agent performs the upgrade the way it performs any other work — upgrading the workflow is itself agent work.

The books and posts our shaping practice leans on are never inside the package. The package carries machinery instead: it fetches the freely published sources from their authors’ own sites at install time, and for the one commercial book it asks for the user’s own copy — when none is provided, the skill is generated with our own distilled account of that book’s method, written in our own words.

And this repository is the first consumer: the workflow’s own home installs the package, configures it, and works under the very rules it ships. The project’s last build stage then migrates our three active projects onto the package — the install replacing everything each of them grew by hand. That migration is the framing’s outcome test run for real: three different stacks, three different configurations, no capability lost — and it doubles as the quality assurance pass, because any gap between what the package generates and what a project relied on surfaces there, before anyone else adopts it. The migration’s per-project details — each project’s configuration values and the behavior deltas it accepts — live in a plan the user keeps locally, outside this repository, because those details are exactly what the privacy rule keeps out; the build asks the user for it when the migration begins.

Walkthrough

Replay the framing’s story — the same person, the same moment — with this in place. Step by step, so the reader can check it against how the work really goes.

  1. An agent in one project trips over something — say, that one-line shell mistake — and the lesson is learned. Two things happen at once. The project fixes itself: a pull request — a proposed change, reviewed before it merges — lands the lesson in the project’s own content, so the problem is solved today. And the lesson is filed as a detailed issue on the package’s home: the full scenario that taught it, anonymized, with suggested changes offered as exactly that — suggestions. There the lesson is shaped — accepted, reshaped, or declined — and what survives is written once, into the package’s source.

  2. A new version of the package is released.

  3. In each project, an agent performs the upgrade: it reads the version’s notes, adjusts the configuration if the notes ask for it, and regenerates every instruction file. The lesson now exists everywhere.

  4. The next session in any project carries the warning. The mistake that once cost an afternoon in a sibling project cannot repeat anywhere — the warning travels by default, not by memory.

  5. And when a new project joins: install, configure, generate. The full way of working arrives in minutes, current to the latest version, with nothing copied by hand and nothing to prune.

Time bombs

The places where this could blow up mid-build. Each one is defused here, in this document, before the build starts.

The package is public, but the shaping practice leans on books and posts that belong to their authors.
How we defuse it The package distributes machinery, never texts. Freely published sources are fetched from their authors’ own sites on the user’s machine; the one commercial book is built only from the user’s own copy, with our own distilled account as the fallback; every built corpus lives only on that machine, never saved into the project’s recorded history; and the repository’s history was recreated clean, with open-sourcing set to publish from a fresh repository.
Configuration sprawl quietly reintroduces the drift this project exists to kill — every option doubles the space of generated output nobody has read.
How we defuse it An option exists only where a genuine, durable difference between projects demands one. Our active projects’ configurations are the tested combinations, and an option no project uses gets deleted.
A breaking upgrade strands a project on an old version because nobody wants to do the migration by hand.
How we defuse it Upgrades are agent work. The package ships a skill about itself, and every version arrives with migration instructions written for an agent to execute.
Someone hand-edits a generated file, and the edit silently dies on the next regeneration — or worse, survives as a local fork.
How we defuse it Generated output is never saved into the project’s history — it cannot be committed, only rebuilt — so a hand-edit cannot survive; the only doors for change are what the project commits (its configuration and its own content) and the package’s source.
The unified instructions bloat: merging every project’s hard-won rules produces doctrine that taxes every session’s attention forever.
How we defuse it Rules only one project learned merge in — unless a rule exists only to compensate for a degraded orchestrator, which is bloat, not refinement, and is dropped. Where variants disagree about the same rule, the leaner text wins unless the longer one demonstrably changes behavior.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • No adoption smaller than a layer. A project cannot pick individual pieces à la carte; a layer comes whole or not at all, because its pieces reference each other.
  • Not a marketplace. The package ships the Seasoned workflow and nothing else — it is not a general registry for third-party skills.
  • No copyrighted text ever ships in the package or enters the repository, even while it is private.
  • The growth-frameworks material some of our shaping corpora carried, and the talk and interview transcripts, are out of the workflow entirely.
  • Deterministic size-testing of instructions — machinery that measures and bounds how much context the workflow itself consumes — is a future project, not this one. Here we only hold the line by judgment.
