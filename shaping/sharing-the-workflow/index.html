Sharing the workflow

Make the workflow something a colleague can pick up and truly understand — how to run it, why it works this way, and where it is going — without its author in the room.

Not built yet Built

Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

A peer from outside the company recently looked at one of our open-source codebases, built with this way of working, and asked how it was possible. There was nothing to send him. The honest answer took a live conversation, and it came in three parts: first, the agents build on a stack and a set of patterns the author spent five years curating by hand before AI; second, everything that needs taste runs on the one model that has it, and that taste is written into the workflow’s skills; third, the author is paranoid about managing the agent’s context window — the limited space that holds everything the agent is working from at a given moment — and that paranoia, why it matters and how it is exercised, exists nowhere in writing. The peer got a good conversation. He did not get anything he could read again, go deeper on, or adopt — and the next person who asks will cost the same conversation over again.

Today’s way, and where it breaks

Today there is exactly one way to learn this way of working: its author explains it, live, one person at a time. Nothing written stands in for that conversation. The package’s README speaks only to a reader adopting the package — readiness, install, upgrade, and a bare list of commands — and never says what the workflow is as a way of working. Everything else in the repository is written for the agents that execute the work, in a dialect tuned for machines, not for a person reading over coffee. The workflow’s goals live only inside its founding shaping document, where no newcomer would think to look — and the vision it is building toward is not written down anywhere at all. So the people closest to it — the ones already running it daily — operate it without grasping the full arc, and anyone further out has no way in at all.

The outcome test

The next time someone asks how we did this, the answer is a link, not a meeting. A peer with no context reads the material end to end and comes back either running the workflow on their own project or asking questions that start where the writing ends — not questions the writing should have answered. And closer to home, the test that decides: a co-founder runs a full working session — including spotting the right moment to compact the agent’s context and running the ritual that makes it safe — without asking the author anything. A peer installing the package unassisted is a delighted extra, not the bar: adoption depends on their own codebase’s readiness, which this project does not control.

Why now

The workflow just became a package anyone can install — and the circle of people meeting it is widening right now. One co-founder already works in a project that runs it daily; another, long used to working AI-first, is next; and beyond them stand industry peers whose feedback would sharpen the workflow while it is still young and cheap to change. None of them can be handed anything today but a conversation. Every week without a written way in, the author stays the only bridge — the exact failure the workflow itself was built to end for code.

The big hire and the little hires

The big hire is the decision to sit down and read the whole thing. A peer holding the link, or a co-founder told “it is all written down now,” has to believe the reading will pay. What earns that belief is the material itself — the project and the vision it serves, presented plainly and well — never a claim about our results. The question that sparked this project stays here, in this document: the written material answers it without ever posing it, and it never boasts.

The little hires are every return visit mid-work: a co-founder mid-session watching for the right moment to compact the agent’s context, someone checking what a command does, someone halfway through adopting who needs to know what a configuration option assumes. Each of those moments has to answer in under a minute, or people fall back to asking the author — and the old way wins again. The two hires pull in different directions — one wants a narrative read whole, the other a reference you can land in the middle of — and the solution has to serve both rather than average them into one document that does neither.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

All the written material lives in this repository, readable right on GitHub — no website, because the audience today is people we send the link to, not people who find us. A new docs/ folder carries the body of it, and the README becomes the front door: it opens with what the workflow is, the goals it serves today, and the vision it is building toward, told plainly in the new voice, and then routes each reader by what they came for — understanding the way of working leads to the teaching material, adopting it leads to the readiness-and-install material the README already does well, and looking something up leads to the reference. One file could never serve both hires; the front door plus the folder serves each without averaging them.

The tagline

One line names the project everywhere a stranger first meets it, set as the GitHub repository description, set as the package’s own description on the npm registry, and opening the README: “Seasoned’s skills to orchestrate the full product cycle with AI agents”. It states the future the workflow is building toward, not only what exists today, and its double meaning is deliberate: the package ships skills, and the company’s accumulated craft is the other kind.

The voice: a docs-copywriting skill

Every human-facing page is written under one guide: a skill named docs-copywriting, committed in this repository and never shipped with the package — the voice of our documentation is ours, not something every adopting project inherits. The register it sets: a developer sharing what they know with a peer, plainly and warmly — not a company presenting, and never a system talking to itself. Because this voice is the project’s biggest risk, the skill was not left for the build to write: it is already authored in full, in this project’s references/docs-copywriting/ folder, adapted from a battle-tested guide and reviewed before this document was approved. The build copies it into place verbatim.

▸ Contract The rules the authored skill carries

The mechanics that traveled from the battle-tested guide: sentence case for every title and heading; specific over vague; problem before solution; the banned corporate jargon list (leverage, seamless, robust, best-in-class, and kin); em dashes spaced and rationed to one or two per page; short declarative sentences followed by longer explanations; fragments and rhetorical questions used sparingly. Left behind: every product-specific layer — speed messaging, calls to action, pricing and onboarding copy, audience templates.

Written new for this repo: no AI dialect — words like “load-bearing”, “binding”, “doctrine”, “surface”, and “charter” do not survive into human docs, and the skill carries a translation table from workflow dialect to plain speech; every term of art the docs genuinely need is defined the first time a reader meets it; honesty about unsettled practice; and the docs never boast — the work speaks, the copy does not point at it.

The authored skill in references/docs-copywriting/ is the single source: SKILL.md plus references/voice-guide.md. The build installs it at .claude/skills/docs-copywriting/ by verbatim copy, verified with diff -r, and never rewrites it.

The teaching pages

Two pages in docs/ teach the way of working: one narrative for the reader meeting it whole, one manual for the person operating it. The way of working is the narrative read whole: what happens from the moment an idea arrives to the moment it ships, with the goals and the vision in their own words and the workflow’s reasons — the curated foundation agents build on, everything that needs taste running on the one model that has it, with that taste written into skills, and care for the agent’s context window — woven through as how the workflow thinks, never as what it achieved. A worked example — one project followed from idea to release — is welcome where the writing calls for it, never required. Running a session is the human’s manual, the piece that exists nowhere today: what the person actually does while agents work — decide, adjudicate, read the changes, merge — and above all how to manage the agent’s context window: why letting it fill quietly degrades the work, how to see that coming, and how the two new skills below fit the rhythm. A third page, Adopting the workflow, receives the readiness checklist, the install walkthrough, the reference-library setup, and the staying-current guidance the README carries today, rewritten in the voice, so the README can become a true front door. The README’s commands table folds into the reference’s commands page, and what its closing section says about this repository folds into the front door itself — every section the README carries today lands in a named home.

▸ Contract How work enters the system — the map the first page teaches

The premise is Shape Up’s: well-planned bigger batches beat a treadmill of tasks. Work is deliberately batched up into shaped projects rather than broken down into tasks. Two entry points feed shaping: a raw idea brought straight to a shaping session, and meeting recordings — one or a batch, sometimes joined by existing issues — parsed into request documents that become shaping raw material.

Exactly two kinds of work skip shaping. Urgent fixes — the Andon cord, in the Lean Manufacturing sense — run as tasks with full rigor: the complete Definition of Done and full orchestration, no shaping. And quick mode, explicitly invoked by the user, covers two cases: small polish to work already done, and research mode — exploring solutions toward a proof of concept when there is not yet enough understanding to plan, with code that sometimes merges. The shipped quick skill qualifies only the polish case today, so this build extends it with the research case — the one deliberate edit to existing agent-facing language this project makes, so the skill and this map agree. Everything else goes through shaping.

Where we part from Shape Up, the page says so plainly: agents do the building, so build time is no longer the scarce ingredient and appetites are dropped; betting is gone too, because opening a shaping session is itself the decision to do the project; and shaping now takes longer than building (the departures the shaping practice already codifies, each with its own reason). The page is also the first written home of this map — today it exists only in practice and in this document. And self-improvement — deriving a finished work’s lessons and feeding them back — runs without anyone starting it: at the end of every task outside a goal, and once per goal when the goal is met. Only quick mode skips it.

▸ Contract The three watches — the second page’s spine

A shaped project’s build always starts the same way: typing /goal plus the goal text pasted from the document. From that moment the person’s whole job is three watches, and they are away from the keyboard for most of the effort — the craft is knowing which moments not to miss. The manual says plainly where /goal comes from — it is the coding harness’s own feature, not something this package ships — and the adoption page lists it among what the workflow assumes about the reader’s setup.

The context window. Once the orchestrator’s context passes roughly 22% full — a little before the context bar in the status line turns yellow — start looking for a moment to compact without interrupting much, usually while it waits on its subagents. Once it passes roughly a third full (33–36%, the bar red), interrupt and compact anyway. The numbers are ballpark; the gesture is what matters: start hunting for the moment before the bar turns yellow, and never let it sit red. The manual also names why this watch belongs to the person at all: the package switches the harness’s automatic compaction off in every project it manages, so the compaction the person runs is the only compaction there is. The ritual: ask whether the ledger is up to date (/prepare-for-compaction); when the orchestrator answers that it is safe, compact, and immediately queue the next message — “Please reground after compaction” (/reground) — so regrounding fires the instant compaction ends, even with nobody in the room.

The usage limits. Watch the subscription’s limit approaching; when it nears, open a second session in another tab and log in to another subscription. Stated honestly in the docs: this way of working is token-intensive — plan on more than one top-tier subscription and learn your own number from how much of the workflow you adopt and how much you shape and build.

The questions. Whenever the person may be away, the workflow has the orchestrator ask through questionnaires, because only a questionnaire pauses the goal loop — a plain question in conversation gets run over by “goal not met, continue.” At the keyboard and conversing, it is plain conversation. A well-shaped project asks few questions either way; the person checks in from time to time to unblock.

And one discipline held as firmly as the three watches: never run or test the product mid-effort, and never micromanage the orchestrator. Test only after the goal is marked achieved. When the result misses expectations, the lesson usually belongs to the next shaping session — though degraded model service happens too, so judge carefully what actually went wrong.

▸ Contract After the goal — verification and release, told honestly

This contract splits across the two pages: the person’s after-goal procedure belongs to the manual; the release landscape and the closed loop belong to the first page’s arc and vision.

When the goal is marked achieved, verification leans on the demo videos first: generate them, watch the full walkthrough, and test by hand only what feels off. A full demo that plays well means the process held — move toward deployment. Running the project locally happens sometimes, but the lean is videos first.

Shipping today usually means a GitHub release — the default branch is not production. The practice around environments is in motion: the likely near-term model is three tiers (everything on the default branch, a staging that takes an explicit action, and a production cut by release), wanted because the more the agents build alone, the more stakeholders need a place to try the work before it ships. And even that may be superseded: the aim further out is a closed loop — observing the running product, users asking the AI about it and sending feedback through it, progressive rollout behind feature flags — where data from the outside world opens the next shaping session directly, instead of server environments standing in as approval gates. That closed loop belongs in the vision passages of the first page.

The ruling for the docs: present release as an area with more than one right way — describe today’s practice, mark the frontier as evolving, and never teach an unsettled rule as settled.

Two tiny skills: /prepare-for-compaction and /reground

The compaction ritual gets two named commands, shipped with the package to every project and meant to be typed by the person, not the agent. They are deliberately almost nothing: today, plainly asking “Is your ledger up to date? I want to compact your context now” and “Please reground yourself after compaction” already works perfectly, because the standing instructions teach the orchestrator what each one demands. So each skill is essentially that sentence with a name — the first has the orchestrator make sure its ledger is current, updating it on the spot when it is not, and then answer plainly that compacting is safe, the second has it reground from the ledger and the real sources of truth after a compaction. The manual tells the same story from the person’s side: prepare, wait for the safe answer, compact. What the names buy is discoverability: a newcomer learns the ritual by seeing two commands exist, and the human’s manual and the two skills name the same commands and the same steps — spot the moment, prepare, compact, reground — while the numbers and the why live in the manual alone.

▸ Contract Content files become optional — so the upgrade costs nothing

Every generated skill reads an optional per-project content file — extra instructions the project may add — but today the package requires the file to exist even when empty. Adding a skill therefore breaks every project’s next sync until it commits an empty file, and consuming projects accumulate rows of zero-byte files. This build makes every content file optional, the doctrine file included: a missing file simply means the project has nothing to add. The one protection the loud failure gave by accident — a misnamed file getting noticed — is replaced by a better one: sync fails when the content folder holds a markdown file matching no known name, so authored instructions can never silently fail to load. The known names are the content files of every enabled skill, the doctrine file, and any file the configuration itself points into the folder — the calibration file already lives there today. With that, the two new skills ship with no migration step, and every consuming project may delete its empty files.

The reference

The little hires get four pages under docs/reference/, each answering in under a minute: the commands (all seven, every flag — several exist today only in --help and the source); the configuration file, key by key, with a real example (today no page documents it key by key — the README covers a handful of options, and the complete schema lives only as comments beside the source types); what a project receives — the generated files, the skills by tier with one line each, and what stays committed versus generated; and the managed footprint — the settings the package enforces, the ignore entries it maintains, the one script it wires. All of it written by hand, in the voice: generated reference prose would read like a manual page, and the mid-work reader deserves better.

▸ Contract The reference cannot rot — enforced by machinery and by the Definition of Done

A hand-written reference drifts the first time a flag is added, so the defusal is a test, not discipline: a unit test enumerates the real surface — commands and flags from the CLI program itself, configuration keys from a key manifest this build adds and exports beside the configuration types (today the keys live only in the exported types, which nothing can enumerate at runtime; the hand-written validator covers only part of them), and the package’s runtime exports (defineConfig belongs to the configuration page; the stack-audit helpers to the what-a-project-receives page, beside the generated skills that teach them) — and fails when any name is missing from the reference pages. It complements the existing golden snapshot of the command surface rather than replacing it: the snapshot keeps pinning command names and descriptions, while this test ties the full surface — flags, keys, and exports included — to the docs. The prose stays human; the names cannot silently rot. The test lands with this project, so the baseline includes the reference’s integrity from day one.

Alongside the test, this repository’s Definition of Done gains a standing criterion: documentation is kept current in the same task that changes behavior — a change to a command, a configuration key, the generated output, or the way of working itself is not done until the docs say so too.

  4. They read the human’s manual: the three watches, and the compaction ritual — spot the moment, prepare, compact, with the reground message already queued.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • No rewriting of the agent-facing content — the standing instructions and the shipped skills keep the language they have today; the two new skills and the new Definition of Done criterion are additions, not rewrites, and the quick skill’s research case is the one deliberate exception, made so the skill matches the entry map this document teaches. Bringing the same plain-speech principles to them is a project of its own with its own constraints (a skill must also stay lean in the agent’s context window), and it is coming later; the name docs-copywriting deliberately leaves room for that sibling.
  • No website and no public promotion — the material is written to be read on GitHub by people we send the link to. A public face is a future project.
  • No case studies, benchmarks, or showcase sections — the no-boast rule stated structurally, so a “who uses this” page cannot appear later without reopening this shape.

How the build starts

The goal

The text that ignites the build, ready to paste, with a live count against its 4,000-character limit. 

Make the workflow something a colleague can pick up and truly understand — how to run it, why it works this way, and where it is going — without its author in the room.

Your first instruction: read shaping/sharing-the-workflow/index.html in full, every technical note open. It is the single source of truth for this build; where anything else disagrees with it, the document wins.

Build, in this repository, against main:

3. The docs/ folder: "The way of working", "Running a session", and "Adopting the workflow", plus docs/reference/ with its four pages — commands, configuration, what a project receives, the managed footprint. Every page written under the docs-copywriting skill, and every contract the document anchors to these pages satisfied in full.

4. The two package skills, /prepare-for-compaction and /reground, in the core tier every project receives, as thin as the document rules them. Done means:

- The document's outcome test is the bar the material must be written to: a reader with no context gets the full arc from the docs alone, and a person running a session finds every gesture the manual promises.
- The walkthrough replays in the shipped material, step by step.
- The closing audit runs as part of this goal, never as a follow-up: audit the complete implementation against the document, section by section — every element, every contract, every time bomb defusal, every no-go — and fix every shortfall before calling the goal met.

Constraints: the no-gos are binding — no rewriting of agent-facing content, no website or public promotion, no case studies, benchmarks, or showcase sections. When the work ships, flip the document's built bit to true.
