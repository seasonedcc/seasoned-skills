Shaping document

Agent instructions

Give the workflow a guide for writing the instructions agents read, and checks that hold every skill to it: every new and changed skill from the day it ships, and every skill once we end the transition.

Not built yet Built

Why this matters

The framing

The problem this project sets out to solve, and how we will know it is solved — told in the words of the people who live it.

The struggling moment

Daniel stewards the workflow this repository ships: the written instructions — the skills — that our agents read before doing any piece of work. By late August 2026 the backlog of recorded lessons had reached 184 open issues, most arriving with suggested wording ready to fold in, and Daniel had a clear vision for improvements beyond them. He opened a shaping session to plan that next round — and stopped before the first question. Almost every lesson would land as a new paragraph on instructions that are already too long: the corpus stands near 74,000 words, the orchestration skill alone near 9,500, and an agent that reads too much before starting works measurably worse. Folding the lessons in as filed would make the workflow worse, not better.

Today's way, and where it breaks

New instructions arrive from two directions. When a skill is born, someone on the team asks an agent to write it — and the agent writes with no guide for how agent-facing prose should sound or how long it may run: the workflow has exactly such a guide for its human-facing pages, and nothing for the far larger body of prose the agents themselves read. And every finished task runs a self-improvement pass that files its lessons as additions: a new rule, a new warning, a new paragraph, each individually reasonable. Nothing pushes the other way. No tool measures how big a skill has grown; the one size rule on the books — keep a skill under about five thousand words — sits inside a skill and is enforced by nothing, and the largest skill is nearly double it.

It breaks in review. These instructions are for humans as much as for agents: a person reviews every change to them, and a person is who each rule must convince. Yet the prose arrives in an AI dialect — a register dense with the agents’ own shorthand — that the reviewer has to translate before they can even judge, and the workflow’s existing guide for human-facing pages, whose translation table makes exactly this dialect mechanical to spot, stops at the docs and never reaches the skills. Size raises the wall higher still: judging a change means holding the whole skill in your head to see whether the new rule is already there in other words, contradicts a neighbor, or belongs somewhere else — and at today’s sizes nobody can, so additions pass and deletions almost never happen. The record shows where that leads: one lesson codified across ten separate issues in as many places, skills that contradict themselves, and rules kept alive only to compensate for weaknesses long gone.

The projects that use the workflow repeat the pattern on their own side: each adds its local instructions on top, with no bound on how much, and upgrades never prune what the package has since absorbed — so the same rule ends up stated twice, in slightly different words, drifting apart.

The growth has a direction bias, too. Nearly every filed lesson is born from something going wrong, so the corpus teaches prevention far more than it teaches creation — and models and people alike drift into guarding the downside above all. Preventing mistakes matters, but it is not what the instructions are for: their highest return is teaching how to produce amazing work and how to invent, and any rewrite of them must be judged by the upside it creates before the failures it prevents.

One truth bounds everything above: the workflow, big skills and all, works. It carries our projects every day, and the failures its rules exist to prevent stay prevented. The problem is what the size costs and what it blocks — never what the instructions do for us. Any cure that loses what they do is worse than the disease.

The outcome test

Five things have to be true afterwards, each checkable without asking us.

  1. Nothing that works today is lost. The workflow keeps doing for us what it does now — it is doing wonders even with the big skills, and no slimming is worth breaking that. The slimmed instructions still deliver everything the old ones deliver: the quality of work they teach, the inventions the improvement channel keeps producing, and the failures they prevent. The observable trace: in the efforts that follow, the work stays at the bar we hold today, and the lessons the corpus already carries do not get re-learned the hard way and re-filed as new issues — a re-filed lesson we once had is the alarm that a cut went too deep.

  2. The postponed session opens. The day this ships, Daniel starts the shaping session this project displaced — working the backlog of recorded improvements — and folding a lesson into a skill no longer fights the corpus. The exact session that could not open in August opens.

  3. The rules hold mechanically on every new and changed skill. Every skill born after this ships, and every skill a change touches, passes the checks — in this repository and in every consuming project — and a change that fails them is blocked by tooling instead of depending on anyone’s discipline or memory. Skills nobody touches may keep failing until the transition ends.

  4. Changes become reviewable, and deletion becomes normal. A person can read any skill, and judge any proposed instruction change, in one sitting — the prose in plain language, with nothing to translate. And over the months after shipping, the changes that land on the corpus delete and rewrite as often as they add.

  5. The transition ends cleanly. The day every skill in a project passes, the project turns one setting on, and from then on every skill — the package’s and the project’s own — is held to the rules, with nothing breaking the day it flips.

Why now

Every improvement we want to make — the 184 recorded lessons and the vision beyond them — lands as prose on this same corpus, so until the corpus can absorb change without growing sicker, every other project stays queued behind this one. The cost also compounds on its own: every agent, on every task, in every project that uses the workflow, reads these instructions before starting work, and the pile grows with each finished effort — the newest third of the backlog arrived from a single one.

The big hire and the little hires

The big hire is Daniel’s, made once: adopting the new discipline into the workflow — the writing guide as a binding rule, the size budgets as enforced checks, every skill passing as the new baseline. What earns that switch is the outcome test’s first item: proof that nothing the workflow does for us today was lost in the slimming.

The little hires are made daily, and they are where this lives or dies. Every agent writing instructions — a skill rewrite, an improvement pass, a project’s local additions — has to choose the guide’s plain, sized prose over the dialect it would produce by default; the guide and the checks must make the right way the easy way. And every person reviewing an instruction change has to keep finding that one sitting suffices — the day a review requires translation again, rubber-stamping returns, and with it the additive-only drift. Agents reliably re-hire whatever the enforced path is, so the little hires that can genuinely be lost are the human ones.

What we will build

The shape

The solution at the level of what people see and do. The drawings are rough sketches of how it works, not of how it will look.

In plain language

We’ll give every instruction an agent reads a written standard and a machine that holds it to that standard. The standard is a skill, agent-instructions, which takes the place of today’s skill-management. The machine is a set of checks — size, shape, and plain prose — in a new command that agents run before they commit and that every pull request’s gates run again. We won’t rewrite the skills we have. Every new skill is born under the standard, and an existing skill is held to it the first time a change touches it; the skills nobody touches keep working exactly as they do today until the transition ends.

The standard

The standard opens with the rule that anchors everything else: every change to the instructions argues its case in the pull request that carries it, whichever direction it points. The case never enters the instruction text, which keeps only a rule’s scope and reason; the pull request keeps the case for changing it, where a reviewer judges it. An addition names the upside it creates or the live failure it prevents, and shows that the rule is not already on the books in other words and would not serve better as tooling. A deletion argues why the text is dead: it compensated for a weakness that is gone, duplicates a rule stated elsewhere, teaches what every model already knows, has been absorbed into tooling, or teaches nothing about creating the upside or preventing a live failure. And a cut is judged with the same care as a growth, because budget pressure makes every sentence look dead: before cutting a sentence, the author thinks hard about what goes wrong without it, and when the sentence is a rule, whether the cut itself breaks it. The guide learned that the hard way while it was drafted, when its own sentence saying the meaning has to survive every cut was the first thing a cut removed. The same bar binds every rethink a first change brings and every change after it — the checks stay as the backstop, but every cut and every growth defends itself at the moment it is made.

Judging that case is never the author’s own job. Every change to an instruction file goes through a fresh-reader cycle before a person sees it: a reader with the agent-instructions skill loaded and no memory of the edits first understands the file deeply, why it exists, who loads it and when, why each section is there, and how it relates to the other skills, well enough to say what the whole does for its reader that no part does alone, and what goes wrong without any part, and understands the change the same way, what its author meant to achieve, from the case the pull request argues. Only then does it read every touched file whole, never the diff, and report where the change or the file fails. The question is whether the change serves the file’s intent, never whether a sentence matches a principle: a sentence can pass every principle and still teach what another skill owns, or name a thing its reader never acts on, and a review that matches principles asks for every term defined and every tool named, each finding right alone and all of them together past the budget. The author judges each finding under the change bar, like any other change, never at face value, and fixes or declines it in the pull request. Two errors rank the judgment: bloating the file is worse than leaving it slightly imprecise, and removing essential information is worse than either; then a new fresh reader reads again. The cycle ends when the author is satisfied with the file, not when a reader runs out of findings. It is a cycle, not a pass, the way the review loop in the Definition of Done is. The rule was earned during this project’s own shaping, twice. First, every finding the person raised on the draft skill was a rule already written in the file, broken by its author editing one sentence at a time. Then the cycle itself overshot: five rounds of rule-by-rule findings grew the draft from 1,873 to 2,215 words, past its budget, with a section re-teaching the pipeline the package’s own skill already teaches, a line describing a feature no project used, and a tool named by its engine and its rule’s internal name — each accepted by an author taking findings at face value, and each removed again when the person read the file whole.

The guide gets a home that already exists. The writing guide for agent-facing instructions does not become a new skill: it becomes the heart of the reworked skill known today as skill-management, renamed agent-instructions — because it now governs every instruction agents read: the skills, the always-loaded rules in CLAUDE.md, and the local additions each consuming project layers on. One skill, loaded for any act of instruction-writing, carrying structure, prose, and size together — and every size check points at it when it fails. It does not re-teach how the files are generated: the seasoned-skills skill is the home of the pipeline, from the configuration to a failed sync, and agent-instructions defines the sync and the check in a sentence each and points there, under its own one-home rule. The dialect agents produce by default is caught by the linter, not by a table in the skill: the rule files hold the words and their replacements, and the check names both when it fires, because a list that lives in the skill and in the rule is two homes for one rule, and a skill that quotes the words it bans fails its own check. The repo’s guide for human-facing pages, docs-copywriting, stays what it is; agent-instructions inherits its voice by starting from a verbatim copy of its text — years of adjudicated input live in that voice, and everything reusable is reused — edited only where agent-facing prose or the size budget demands, and never by pointing at a file consumers do not have. The voice guide the skill carries as a reference file inherits the same way, and then has to pass every rule the skill states, the sixth-grade ceiling included: its spirit stays, but its example sentences are rewritten, because the founders’ own prose the guide quotes reads above the ceiling and a reference file is checked like any other. We rewrite it during this shaping, once the skill itself is settled.

The checks

The budgets, and every other check, bind the text each owner writes, as the section on owners below sets out. The numbers are package-versioned constants — tuning one is a release, never a local edit. The budgets reach a skill’s reference files too, each with 2,000 words of its own and the writing guide binding it — otherwise a budget on skill bodies would only push the overflow into the references, hiding the bloat instead of removing it. The check lives today in this project’s references folder and fails the file with the guide’s own three moves in its message; ten of the package’s thirty-one skills fail it as they stand, orchestration at nearly ten thousand words, and the agent-instructions draft fits at 1,769. Scripts are code, checked by the code linters the repository already runs.

Not everything a skill carries is instructions, so a project can tell the check to skip a file. Three projects keep verbatim third-party texts inside their own skills — marketing books, health-privacy regulations, Brazilian privacy law in Portuguese — which our rules require byte for byte and no lint may touch; another keeps a research data set of generated comparison tables and customer reviews quoted word for word. The line is between instruction prose an agent follows and material a skill reads. A project lists what to skip in its configuration, each entry with the reason it is not instructions, and the check prints that reason whenever it skips a file, so every exemption stays in front of a reviewer. Three guards keep the list from becoming a way around the transition. The check refuses an entry that covers a skill’s main file or a project’s addition to a package skill or to CLAUDE.md, so only supporting files inside a skill’s folder can be skipped, never the text an agent loads every time. An entry that matches no file fails the check, so an exemption leaves with what it excused. And adding an entry is a change like any other, arguing its case in its pull request. The package keeps its own list the same way, in this repository’s configuration, and it holds one entry today: the complete documentation of the composable-functions library, a 3,073-word verbatim copy. The shaping corpus needs none, because it is built onto each machine into generated folders the check never reads.

The check holds six things about the shape of a skill, not only its length. A skill’s name follows the open Agent Skills specification: one to sixty-four characters, lowercase letters, digits, and hyphens only, never starting, ending, or doubling a hyphen, and matching the skill’s folder — today the build guarantees the match by construction, and nothing checks the characters. The description stays within 1,024 characters: Claude Code truncates a longer one at 1,536 and cuts from the end, which is exactly where the “use when” half lives, and 1,024 is the open specification’s own cap. Em dashes are rationed the way the voice guide already asks, as a number the sync can count: none in the front matter, at most two in any generated file or reference file. Lists stay flat: a list item nested inside another fails the file, since each level is one more thing for a reader to hold, and the fix is a subheading over a flat list or a rewrite as prose. Today two skills and one CLAUDE.md fragment nest lists, and the guide’s own draft nested nine items before the check existed. A reference file the skill’s body never names fails the file too: a reference file costs nothing until a step in the body sends the agent to it, so one no step names is dead text nobody reads. And a reading-grade ceiling holds the sentences short: the generated file, with its front matter, headings, tables, and code stripped, scores no higher than sixth grade on the Flesch-Kincaid scale, a plain formula over words per sentence and syllables per word that any open-source library computes the same way every time. A spike settled that this ceiling is reachable without dumbing anything down: the agent-instructions draft went from grade 7.8 to 5.4 by splitting sentences alone, with the same word count, the same vocabulary, and no rule dropped. The ceiling is per file, never per sentence: the formula punishes a long word in a short sentence, so a three-word heading can score at grade twelve. The generated description is scored on its own under the same ceiling, because it is the one part of a skill every agent reads on every turn, and the draft’s own description scored at grade eleven before its two sentences became four. Every check fails the way the budgets fail, naming the file and the line and pointing at agent-instructions, and every one binds a text from the first change that touches it, since today’s skills break them all — the orchestration skill alone carries over a hundred em dashes.

The grade ceiling proved that a formula can carry part of the editing, so the checks grow a prose linter beside it. The engine is Vale, an open-source linter for prose whose rules are small, readable files, so the standard itself is something a person can review. The package ships it through its npm wrapper, carries our rules as one Vale style, and installs both into every consuming project as part of the managed footprint. Every rule fails the file, the way the budgets do, and there is no second tier of warnings: the dialect translation table, the jargon and hedging lists, shouting, sentence case in headings, a cap of thirty words per sentence, spelling against a project dictionary, blocks of prose repeated verbatim across files, links between files that no longer resolve, and a skill referred to by anything but its roster name. A rule earns its place by measurement: it runs over our own files first, its hits are read by hand, and it turns on only when every hit was real. A rule that cannot get there is deleted, never demoted to a warning, because a warning misguides agents in two ways we watched happen: an agent treats it like a rule and applies it everywhere, rewriting approved sentences to silence it, and a rule that can be satisfied mechanically gets satisfied mechanically, the way the grade ceiling first produced choppy fragments. The first pass, over the thirty-three skills the package carried in September, settled the list: passive voice (523 hits, almost none a defect), vague quantifiers, universal claims, comma counts, contractions, and a part-of-speech rule for words that read as both noun and verb all failed the bar and are gone, while “solution” left the jargon list because twenty of its twenty-three hits were the word’s plain meaning. Text in double quotes is a mention, not a use, so a rule can quote the phrase it bans. The banned words themselves live only in the rule files, never in the skill, so no file quotes what it bans, and the skill keeps only what no check can see. Nor does the skill point at the rule files: the check prints the word, its replacement, and the rule that fired, and it is fast enough to lean on, measured at 0.6 seconds for one file and 4.2 seconds for all thirty-three skills the package carried then. Rules face the change bar like prose: a rule whose failures turn out wrong is fixed or deleted in the pull request that found it. What is left for a person is the reading no rule can take over. A spike settled how Vale reaches a project: its npm wrapper downloads the binary from GitHub when the package installs, and under pnpm 10 only once the project’s package.json approves that step. Without the approval the install succeeds and the check finds no binary. So the sync adds the approval to the project’s package.json, the way it already keeps the sync script there.

Who owns which words

Three kinds of text make up what an agent reads, and each has exactly one owner. The package writes its own text for every skill it ships and for CLAUDE.md. A project adds its own words to those skills and to CLAUDE.md through its content files, which the sync weaves in. And a project writes skills of its own, whole, that the package never sees — this repository’s docs-copywriting is one.

Each owner’s text is checked alone, against a budget of its own, and no check ever looks at the other owner’s words. The package’s text for a skill is held to the rules as the package wrote it; a project’s addition to that skill is held to them as the project wrote it. A package release can never push a project over a budget, and a project can never fail on prose it does not own. What an agent loads stays bounded, because it is the sum of two bounded parts. We considered one shared budget on the woven file, and rejected it: whoever wrote last would pay for the other owner’s words, and the transition would need to build every skill twice to tell whose words broke it.

The budgets follow the owners. The package’s text for a skill gets 2,000 words, and a project’s addition to that skill gets 500 more, so the body an agent loads for any package skill stays within 2,500 words. A reference file — a file a skill carries for reading only at the step that names it — gets 2,000 words of its own, never summed with the body, because it loads only when that step comes. CLAUDE.md, which loads in every session before anything else, keeps the 2,500 words it would have had whole, split the other way round: 1,500 for the package’s part and 1,000 for the project’s. What every task needs first is mostly a project’s own facts — its commands, its stack, the rules that hold everywhere in it — and those have nowhere else to go, while most of the package’s part is general practice a skill can carry. A criterion a project adds to the Definition of Done through its configuration counts as the project’s words.

We’ll let a project give a package skill reference files of its own, which today only the package can do. Without them, 500 words would be a wall: a project whose design rules apply on every screen could only split the design-system skill for size alone, which the guide forbids, or lose material. A project’s reference file sits beside its addition, and the sync places it in the skill’s reference folder beside the package’s own. It gets the same 2,000 words and every rule, the project’s addition names it at the step that reads it, and the project’s additions setting covers it. Take a project that adds 2,402 words to design-system today: its date-field rules become a skill of the project’s own, since building a date field is a situation of its own; the detail behind hover-revealed and disabled controls moves to reference files read when someone builds one; and its addition keeps the tokens and a line per rule that every screen needs. An agent building an ordinary screen then loads 2,500 words of design system instead of 6,000, and the project loses no rule it has today.

▸ Contract The word budgets

A word is a whitespace-separated token holding a letter or a digit, so code counts and list markers do not. A skill’s budget counts its body alone, everything below the front matter, because the two front matter fields have caps of their own. A reference file has no front matter and is measured whole. The numbers are package-versioned constants: tuning one is a release, never a local edit. 

package text for a skill (content/skills/<name>/SKILL.md body)  2,000
project addition to a skill (<contentDir>/<name>.md)            500
any reference file, package or project                         2,000 each
  package:  content/skills/<name>/references/<file>.md
  project:  <contentDir>/<name>/references/<file>.md
            → .claude/skills/<name>/references/<file>.md
            refused when <file> matches a package reference file
CLAUDE.md, the package's part (content/doctrine/ fragments)    1,500
CLAUDE.md, the project's part (<contentDir>/doctrine.md,
  plus additionalCriteria text from the configuration)          1,000

The paths above are today’s; the rename below moves the two that carry the banned word. Today, against these numbers: ten of the package’s thirty-one skills are over 2,000 words in their own text, orchestration at 9,931; across the five consuming projects measured, most additions sit under 600 words, and the largest are on testing (2,800 and 3,300) and design-system (2,364). The package’s part of this repository’s CLAUDE.md is about 3,030 words; the projects’ parts run from 234 to 1,475.

Each project ends its transition on its own terms, with two settings. One covers the skills the project writes whole; the other covers the project’s additions to the package’s skills and to CLAUDE.md. While a setting is off, only new and changed text under it must pass; once it is on, all of it must. Two settings, not one, because the two kinds of text heal at different speeds: a project can hold its own few skills to the rules long before it has trimmed every addition, or the other way round.

▸ Contract The settings

One new key in seasoned-skills.config.ts, typed in the configuration’s types, validated with the rest, and listed in the configuration reference like every key. Every project starts with both settings at 'changed'. 

instructionChecks: {
  ownSkills: 'changed' | 'all',   // skills the project writes whole
  additions: 'changed' | 'all',   // its content files and their reference files
  ignore: [{ path: string, reason: string }],
}

In the package’s own repository, ownSkills also covers the package’s skills and its part of CLAUDE.md. ignore paths are relative to the project root and may be patterns; an entry matching a SKILL.md or a content file is refused, and so is an entry matching nothing.

The package’s own transition ends the same way, with no machinery of its own. Only this repository holds the package’s text, and from where it stands that text is its own: it writes the package’s skills and the package’s part of CLAUDE.md whole. So here the own-skills setting covers them, beside docs-copywriting, while this repository’s additions sit under the additions setting like any project’s. The day we turn the own-skills setting on here, the package’s transition is over: from then on every change to the package keeps every skill passing, and every release ships skills that pass.

▸ Contract The package’s text varies with configuration

Some of the package’s text is assembled from pieces a project’s configuration chooses: whether agents may merge during a goal, whether the project is a web application, how out-of-scope findings are handled. The package’s text for one skill is therefore a slightly different text in each kind of project. The check composes the package’s text in every variant the golden fixtures produce (tests/golden/fixtures/, four today, which exist to cover those variants) and judges each variant alone; a skill passes only when every variant does. A change to a piece shared by several skills, or by a skill and CLAUDE.md, counts as a change to every text it lands in.

A change that touches a skill touches all of it. The first time a change lands on text that fails today, that same change leaves the text passing whole — every word under budget, every rule met — not just the lines it came to add. Adding two sentences to the 10,000-word orchestration skill means rethinking orchestration down to 2,000 words in that pull request. That is deliberate: we don’t improve a skill without rethinking it, and a rule added to a skill nobody has rethought lands on the same pile that blocked the backlog in the first place. The rethink is judged the way every instruction change is: each cut argues its case, and fresh readers check that nothing the skill does today was lost. We considered two gentler paths and rejected both for that same reason. A ratchet, where a touched skill only has to not grow, improves a skill without rethinking it, and lets the biggest skills fail forever, so the transition never ends. Healing a skill in a pull request of its own before the lesson lands splits the rethink from the improvement that called for it.

The checks live in one new command, seasoned-skills check, and nowhere else enforces them. With no arguments it finds what changed by comparing the working copy, uncommitted edits included, with the point where the branch left the default branch; it checks every changed piece of text, and all the text of any kind whose setting is on; it reports each failure with the file, the line, and what broke, writes nothing, and exits non-zero. Given file paths, it checks those markdown files as they are, whole, which is what an agent drafting a skill needs before it commits, and what a project needs for a content file before it is woven. The agent-instructions skill tells agents to run it before they commit. It lands in the reference pages and their enumeration test like every other command.

The sync never fails because of these checks, which is a change from the earlier plan to have it refuse to write a file that fails them. The sync runs on every install — on the default branch, in fresh clones, in continuous integration — where nothing has changed and the question has no answer; and a failed sync takes the workflow down with it, leaving everyone in that checkout without their skills. A broken rule blocks a pull request, never an install. So the check runs where pull requests are judged: the Definition of Done’s gates criterion names it beside the linter, the type-checker, and the unit tests, in this repository and in every project the sync generates that criterion for; this repository’s continuous integration runs it; and both the seasoned-skills skill and the documentation tell every project to add it to its own.

The project also renames everything the new design leaves out of step, in the package and in every consuming project: the content file that feeds CLAUDE.md, today named after a word the dialect rule bans, becomes claude.md, named after what it generates, the way each skill’s content file is named after its skill; the code module and fragments that carry that word follow. A design that bans a word in prose and keeps it as a file name is not cohesive. Prose that uses the word is not renamed with them: it meets the dialect rule the way all prose does, the first time a change touches it. A project that upgrades with the old file still in place gets a sync that refuses it by name and says what it is called now, the way the sync already refuses any content file nothing loads.

No-gos

Things this project deliberately does not do, so nobody has to wonder.

  • Rewriting the skills we have. No skill is slimmed for its own sake; each one heals the first time a change touches it, and the change that touches it carries the rewrite.
  • Reorganizing where rules live: no skill for running goal-driven efforts, no skill for the session ledger, and no restoring of the rules lost in the move to the package. Each of those rewrites a skill’s content, and this project only gives that content a standard to meet.
  • Removing the triggers: line a content file may open with. It stays as it is.
